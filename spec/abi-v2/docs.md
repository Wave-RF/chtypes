# chtypes ABI v2: the prose for the description

This file holds the prose for `spec/abi-v2/abi.json`, one `###` section per handle, enum, function and (optionally) constant or document. `scripts/abi-v1/gen.py --major 2` copies each section into the comment above its declaration in `include/v2/chtypes.h` and into the generated block of `docs/reference/abi-v2.md`, and `gen.py --major 2 --check` fails when a symbol has no section or a section names no symbol. The `## Rules` section below is copied into that block too.

Prose is deliberately outside the fingerprint: editing this file never changes `CHS_ABI_FINGERPRINT`, so it never invalidates a built library. The rule that follows is that anything a binding or the artifact producer must act on is structured in `abi.json` (a nullability, an ownership, a status a call may return, a thread class, an init class, a vocabulary), never only stated here.

The WHERE-affecting settings lists for each supported ClickHouse line are in `spec/abi-v2/where-settings/` (with a README); they are documentation, outside the fingerprint. The consumer rule (v2.0 and later) is one check, stated in `document:schema_description` and in that README: refuse a tenant whose `filter_declined_settings` is not empty.

The catalog of every reason the library declines or refuses a filter, per supported line, is in `spec/abi-v2/declines/` (with a README); it is documentation, outside the fingerprint. A consumer maps a decline it receives to its entry there; the verdict model is `filter_verdict` below.

Each section is copied into a C comment, so it may not contain a comment opener or closer, or two question marks in a row.

**Locked.** `spec/abi-v2/abi.json` declares `stability` `locked`: generation 2's description is final, and its fingerprint no longer moves (rule r9 is how it evolves from here). While it was being designed it declared `unstable`, and the fingerprint moved with every change. It was seeded as generation 1's surface at generation 2; the additions land one pull request at a time. The first is the server profile: the `chs_server` handle, `chs_server_create` and `chs_server_free`, a server and an options document on `chs_schema_create`, and the `server` and `replicated` members of `schema_description`. The second is the batch document's `at_merge` list, with its `merge_reason` vocabulary, and a top-level `unsupported_settings` (public issue #544). The third is the settings a server profile sets that this build's filters do not honor in a WHERE: `schema_description`'s `server.filter_declined_settings`, with its `declined_tier` vocabulary, `chs_filter_create`'s decline on a schema whose server lists any, and the declined names from the other settings layers at evaluation. The fourth makes that one list over every layer known at schema compile (public issue #588): `schema_description`'s top-level `filter_declined_settings`, each entry with its `declined_layer` (`defaults`, `server` or `schema`), replaces `server.filter_declined_settings`, which is removed. **Changed by the fourth:** a declined setting from the `chs_set_defaults` or the schema layer, which the third named at evaluation, now declines `chs_filter_create`, at create time; a filter's own settings and an evaluation's stay evaluation-time. The fifth is one interface batch: `schema_options`' `posture`, with its `posture` vocabulary and `schema_description`'s `posture` (public issue #477); the per-call options document `insert_options`, taken by `chs_preview_row`, `chs_preview_batch`, `chs_block_create` and `chs_filter_eval_body`, whose member `defer_defaults` (public issue #479) is defined and declined until implemented, with the batch document's `deferred` and `export_columns` and `value_src`'s `default_deferred`; the object form `{"b64": …}` for a settings or query-parameter value whose bytes are not UTF-8 (public issue #424), as the content `json_object_byte_values`, and in `schema_description`'s server `settings`; `value_src`'s `fallback` (rule r3); the batch document's `unsupported_settings`, now required; and each function's init class, `any` or `required`, with a `required` call's refusal before `chs_initialize` (the Preamble's Initialization). The sixth is the second interface batch, from WaveHouse's sign-off review: every member the library writes is described and the load-bearing ones required, each vocabulary member bound to its enum (`vocabulary`); `chs_error_reason`, `CHS_CODE_DECLINED` and the `reason` members, so a decline is machine-keyed by its catalog id; the `refusal_site` vocabulary (`call`, `body_read`, `row`, `body_step`) with `refused_at` and `refused_row`, the members present under a condition stated as MUSTs, each with a conformance case, and the five body calls answering every verdict about a call in its document (their `may_return` loses `CHS_REJECTED` and `CHS_DECLINED`); `input:filter_options` on `chs_filter_create`, with `param_encoding` reserved; the column list `columns` on `chs_filter_eval_body`, as on the other calls that model an INSERT with one; `insert_options`' `insertable_columns`, `column_defaults` and `verdict_basis`, and `defer_defaults` with a mixed body declined (`defer-defaults-mixed-body`); `row_spans` one entry per row, and `export_columns` on every export as its one column-list member; `export_declined_reason`, an export decline's catalog id; `at_merge`'s `part_row`; the row document's `unsupported_settings` removed; `chs_schema_describe` guaranteed for a compiled schema; the `server-refuses` tier; `default_support` and `reads` per column, reserved; and rule r9 (reserve and decline), with rule r8 (crashes: the known-crash list and the breaker). What generation 2 adds, and what the lock needs, are in public issue #511.

**Platform requirement.** A caller runs the library on the same operating system and CPU architecture as the ClickHouse server it models: every answer is guaranteed relative to a server on the same platform. On 26.7 and later, every platform agrees. On 26.3, ClickHouse's own parse of Float values from text input formats differs across platforms (macOS, Linux amd64, Linux arm64; mostly 1 ULP), so stored Float values, and comparisons involving them, can differ across architectures (`docs/limitations.md`).

## Rules

These rules bind generation 2 from its first draft: the library, every binding and the artifact producer. They are normative; `MUST`, `MUST NOT` and `SHOULD` are RFC 2119. `scripts/abi-v1/gen.py --major 2 --check` enforces the part of each rule that a description can be checked against, as each rule says. Rules (r5), (r6) and (r7) are binding behavior, which the dev bindings implement in their own pull requests.

**(r1) A growable function takes an options document.** A function that may gain inputs after it first ships MUST take them in one options document, a `bytes_in` JSON object, never as more positional parameters. The library MUST validate that document and MUST refuse a key it does not know with `CHS_INVALID_ARGUMENT`, naming the key; it never ignores one. So a caller that sets an option the library does not implement is told so, instead of silently getting the old behavior. A binding passes the caller's options through and never drops or rewrites a key. The description marks such a function `growable`, and lists its documents under `inputs`; an options document is the entry with `options` true, and a document of fixed purpose (a server profile) has `options` false. Checked by `gen.py`: a function marked `growable` takes exactly one options document (a `bytes_in` parameter whose content is `input:<name>`); a function not marked `growable` takes no input document at all; every input document is a JSON object whose schema closes every object, with `additionalProperties: false` on a record, or an `additionalProperties` schema and no `properties` on a map whose keys are data (setting or macro names); and every input document is taken by some function. The first growable functions are `chs_server_create` and `chs_schema_create`.

**(r2) Readers ignore unknown fields.** Every reader of a result document (each `document:<name>` output, and `chs_build_info()`) MUST ignore a member it does not know, at every object level, `_b64` members included, and decode the rest as if it were absent. Checked by `gen.py`: no document schema and no `build_info` schema in the description closes an object (`additionalProperties: false`). The released 1.x readers already behave this way: measured on the 1.0.4 bindings, all four on 12 CI legs, for every result document at every object level ([`v1-abi` run 37504999630](https://github.com/Wave-RF/chtypes/actions/runs/37504999630), the conformance legs of the unmerged probe, public pull request #509).

**(r3) Every enum has an `unknown(n)` member.** Every enum the description defines, an `int32` enum and a string vocabulary alike (`chs_status`, `chs_format`, `value_src`, `default_kind`, the three outcomes, `filter_verdict`, `transform_reason`, every one), MUST have in every binding an explicit member `unknown(n)` carrying the raw value `n`: the integer of an `int32` enum, the exact string of a vocabulary. A reader MUST map a value its description does not list to that member, for that field alone, and go on decoding. An unlisted value never fails the document, the row or the batch that carries it. Checked by `gen.py`: no described value is spelled `unknown`, `CHS_UNKNOWN` or `CHS_<name>_UNKNOWN`, the name readers reserve for that member.

- **A `fallback` changes meaning.** It no longer names the value an unlisted one is read as: the reader keeps `unknown(n)`. It names whose per-value facts `unknown(n)` reports (`lossy` for `transform_reason`, `answered` for `filter_verdict`) and how a question about the value is answered, so the fail-closed reading stays: an unknown outcome is never accepted, and an unknown verdict is never answered.
- **Facts need a fallback.** An enum whose values carry facts MUST name a `fallback`, so that what `unknown(n)` reports is decided before the description is locked. `value_src` names `skipped`: an unknown source reports `is_stored` false, which is how every dev binding already read it.
- **A call status.** A status outside the closed set reads as `unknown(n)` too. The call still fails, as an internal error naming `n` (the `unknown` entry of `errors.status` in `spec/abi-v2/sdk.json`), because a status a binding cannot read is never a success.
- **Schemas constrain the writer.** An `enum` inside a document schema (`default_kind` in `schema_description`, `framing.container` in `batch`) constrains what the library writes, never what a reader accepts.
- **Why.** Measured on the released 1.0.4 bindings, all four on 12 CI legs ([`v1-abi` run 37506595472](https://github.com/Wave-RF/chtypes/actions/runs/37506595472), the conformance legs of public pull request #509): a reader survives an unlisted value only where its vocabulary has a fallback (an outcome reads as `unsupported`, a verdict as `d`, a transform reason stays raw and reads as lossy), and an unknown call status is an internal error. An unlisted `value_src` fails the WHOLE document with an internal error, so one row's unknown source loses the entire batch; an unlisted `default_kind` fails `schema_description` the same way.

**(r4) Error codes are stable once published.** An error code a caller can match on keeps its name and its number from the first release that carries it, a `2.0.0-dev.N` pre-release included, in every later release of every generation, and is never reused for another meaning. That covers the `chs_status` values, the `CHTYPES_*` codes (`errors.codes` and `errors.fetch_codes` in `sdk.json`, and the fetch layer's table in `docs/guides/fetch-v1.md` §8) and the exit status each code maps to. A new failure gets a new code, with an exit status no published code has. Checked by `gen.py`: every `chs_status` value generation 1 published keeps its name and number, and every `errors.codes` entry of `spec/abi-v1/sdk.json` is kept and none is reused under another key. The fetch layer's table is checked against `spec/fetch-v1/constants.json`, the file §8 is generated from: `errors.fetch_codes` lists every code in it with the same exit status and no code it lacks, every `errors.codes` entry names a listed code, and every code in `spec/abi-v2/published-fetch-codes.json` (what releases have published) is kept under its exit status in both files, and a new code takes a status none of them has. The baseline is a committed file the check reads, never git history. The same holds for the decline catalog's reason ids (`spec/abi-v2/declines/declines.json`'s `id`, which `chs_error_reason` and every document's `reason` and `verdict_reason` carry) and for the sentinel `CHS_CODE_DECLINED`: an id keeps its meaning from the first release that carries it, a retired entry stays in the catalog under its id with a `retirement` naming its successors, and an id is never reused for another meaning. A new cause gets a new id. `scripts/abi-v2/check-declines.py` is where the check belongs, against the published catalog.

**(r5) The cache.** A generation-2 binding's cache MUST be one no released 1.x reader ever reads. The normative fetch specification for generation 2 is [`docs/guides/fetch-v1.md` §"Generation 2 after the lock"](../../docs/guides/fetch-v1.md#generation-2-after-the-lock), and r5 and r6 point at it rather than restate it.

- **Record schema 2.** Its `verified.json` records are `schema: 2`. Released 1.x readers accept exactly `schema: 1` and treat any other record as absent (`docs/guides/fetch-v1.md` §1; the `cache-record-foreign-schema2` conformance cases hold every 1.x binding to it).
- **The default root.** It is `${XDG_CACHE_HOME:-~/.cache}/chtypes/v2-dev/` while the description is unstable, and `${XDG_CACHE_HOME:-~/.cache}/chtypes/v2/` after the lock. Generation 1's is `.../chtypes/v1/`, so the two never share a default root.
- **The system directories.** The read-only directories a binding searches after its cache are generation 2's own, never generation 1's `/usr/local/share/chtypes/v1` and `/opt/chtypes/v1`: `/usr/local/share/chtypes/v2-dev` and `/opt/chtypes/v2-dev` while the description is unstable, and after the lock the pair in the "system directories" row of the section above, whose source is `prod_v2.system_dirs` in `spec/fetch-v1/constants.json`.
- **An explicit cache.** For ANY explicit cache directory, from the environment (`CHTYPES_CACHE`) or from the binding's own cache-directory option (Go `FetchOptions.CacheDir` and its counterparts in the other bindings), a generation-2 binding uses the subroot `<cache>/v2-dev/` (`<cache>/v2/` after the lock), never `<cache>` itself, which a 1.x binding uses as its whole layout. A caller that inspects or pre-populates a cache it named looks in the subroot. The subroot is a MUST, not a SHOULD. The API that reports where a lookup reads (Go `CacheRoot` and `SearchDirs`, and their counterparts) returns the subrooted path, and so does `chtypes where`. A 1.x reader that met a record it cannot read inside its own layout treats it as absent and then re-verifies that entry from the cache's blobs (`docs/guides/fetch-v1.md` §1). A build that only the staging key signed fails that check, as an error, not a miss (`inferred` from that guide, not measured). In its own subroot, a generation-2 build is never in a 1.x reader's path.
- **The result.** A released 1.x reader never picks a v2 build, in the default cache or a shared one, and no 1.x change is needed for that (`inferred` from the record rule and the layout above; the decision is recorded on public issue #508).

**(r6) The dev channel.** While the description is unstable, generation 2 ships only as pre-release SDKs, `2.0.0-dev.N`, which a package manager never installs by default: npm's `dev` dist-tag, PyPI `2.0.0.devN`, crates.io `2.0.0-dev.N`, and Go `go/v2.0.0-dev.N` under the module path `github.com/wave-rf/chtypes/go/v2`. The normative fetch specification for generation 2 is [`docs/guides/fetch-v1.md` §"Generation 2 after the lock"](../../docs/guides/fetch-v1.md#generation-2-after-the-lock), which this rule applies to the dev channel and which holds after the lock. Each one:

- **fetches** ONLY from `https://registry-staging.wavehouse.dev/chtypes/v2-dev`;
- **trusts** ONLY the staging key, the ed25519 public key `5cd30c53c65a1ebc2d85836a41deb06661bb0ae7b658adb9eb116ec2db8e9b1c`, key id `824345f9bcf8e5bf` (`sha256-first16hex`, the algorithm the release key's id uses in `docs/guides/fetch-v1.md`). The delivery side trusts that key only for the `chtypes/v<N>-dev` repositories and never in production, and the release key is not in a dev SDK's trust list;
- **has no override:** neither a base nor a trust list comes from the caller or the environment. `CHTYPES_ARTIFACTS_URL`, `CHTYPES_TRUSTED_KEYS`, `CHTYPES_ALLOW_UNSIGNED` and the API options that set a base or a trust list are not honored, and a dev SDK says so, once and loudly, when one is set;
- **refuses `--lock` and `--frozen`,** and their API equivalents, before any network call: a dev build is replaceable and a superseded one expires, so nothing may pin one;
- **pins its dev fingerprint** and refuses a library with any other, as `CHTYPES_ARTIFACT_INCOMPATIBLE`, with exactly this message, where X and Y are the two full `sha256:` fingerprints: `this SDK speaks dev fingerprint X; the library has Y — update your dev SDK`.

**The offline mode.** Every binding has an offline mode, and its meaning is the same in every generation and after the lock: a fetch reads the cache and the system directories only and makes no request. An installed, verified library is used as it is; with nothing installed the fetch fails as `CHTYPES_ARTIFACT_MISSING`, the code 1.x gives (r4), not as an unreachable source. The mode is the `offline` option (Go `FetchOptions.Offline` and its counterparts, and the command line's `--offline`) or the environment variable `CHTYPES_OFFLINE=1`, its twin: a binding reads it once per call, with the other fetch environment variables, and only the value `1` turns it on. Offline mode is on when the binding's option sets it or `CHTYPES_OFFLINE=1` is set; neither turns the other off. The mode names no source, so it cannot point an SDK anywhere and r6 holds.

**(r7) A closed handle is never passed as NULL.** Some handle parameters may be NULL, and NULL then means something of its own: `chs_schema_create`'s `server`, where NULL is the image's own server, and `chs_preview_batch`'s `filter`, where NULL is no filter. At such a parameter the library cannot tell a freed handle from a deliberate NULL, so the binding is the only place a closed handle can be caught.

- **Refuse, never substitute.** Where a function takes a handle parameter that may be NULL and whose NULL has a meaning of its own, a binding MUST refuse a handle the caller has CLOSED, with its own usage error, before any call. It MUST NEVER pass NULL in its place: a binding that frees a handle by setting its pointer to NULL would otherwise compile with no server and answer `CHS_OK`, a silent wrong answer.
- **A foreign handle is the library's to refuse.** A handle made by another library image is not the binding's to judge. The binding passes it through, and the library refuses it with `CHS_INVALID_ARGUMENT`. This rule covers a CLOSED handle only.
- **Unreachable by construction.** A binding whose type system makes a closed handle unreachable (Rust: a server is freed only on its last drop, and a compile borrows it) satisfies the rule by construction, and says so in its reference.

Checked by two shared conformance cases (`tests/fixtures/abi-v2/setup-cases.json`, generated by `scripts/abi-v1/emit/setup_cases.py`), which every binding that can express them runs through its public API over the stub library: `server.a_closed_server_is_never_passed_as_null` and `filter.a_closed_filter_is_never_passed_as_null`. Each compiles or previews with an open handle (the stub sees a non-NULL handle), with no handle (the stub sees NULL), and with a closed handle (the binding's usage error, where a NULL passed in its place would have succeeded). The server case reads the stub's live-handle counts; a batch call mints no handle, so the filter case runs on the stub variant `filter-observable`, which answers `rows_passed` 1 when a filter reached it and 0 when it received NULL. Rust declares both cases not expressible, with the reason, in the case itself. `gen.py` checks only that this rule is stated (`GENERATION_RULES`), since which parameters give NULL a meaning is prose, not structure.

**(r8) Crashes.** The library runs ClickHouse's own code on the caller's input, unmodified. A crash inside that code is a defect of security severity, like an over-accept, and is fixed or declined with a catalog entry in a later build; it is never documented as acceptable. Until then this generation does **not** promise that no input can terminate the process. What it promises is the following. (1) **The known-crash list.** Every build's release notes carry the producer's known-crash list: each entry names the line, the entry point, the input shape and the issue, and the producer's release gate counts those entries and fails on any crash not on the list. A list that is not empty is stated in the notes of every build that ships the line. (2) **The breaker.** A compile-class call (`chs_schema_create`, `chs_filter_create`, `chs_server_create`, `chs_set_defaults`, `chs_type_validate`, `chs_reference_type`, `chs_discover_columns`) records its input before it runs and clears the record after; a process that dies during the call leaves the record, and the next process of the same build on the same host declines that exact input with `CHS_DECLINED` and the reason id `vendored-crash-previously`, so a crashing input terminates a process at most once per host where the record can be written. Where it cannot (a read-only cache, no writable directory), the breaker is off and the library says so once at `chs_initialize`; `chs_build_info.capabilities.features` lists `crash_breaker`. An input whose shape is on the build's own known-crash list never reaches the code that crashes: `chs_schema_create` and `chs_filter_create` decline it at create, `CHS_DECLINED` with the reason id `known-crash-declined` and a message naming the list's rule id, the line, the clause and what to change. (3) **No wrong answer.** A breaker decline, like every decline, is never an accept and never a server's own refusal; an input the breaker does not know is answered exactly as without it. (4) **The exceptions** r8 does not cover in any generation: misuse the ABI forbids, exhaustion of the process's memory outside the admission budgets, and signals from outside the process. The full guarantee, no input terminates the process through any `chs_*` call, is generation 3's. `gen.py` checks only that this rule is stated.

**(r9) The description evolves by reserve and decline.** After the lock a new input member, document member or enum value moves the fingerprint, so a feature that may follow the lock is reserved in the description before it: its input member is defined and a build that does not implement it declines it at any value but its default (Input documents, in the Preamble), and its output members are defined and absent until a build writes them. Implementing a reserved member is a behavior change, never a fingerprint change, and a build advertises each implemented reserved member in `chs_build_info`'s `capabilities.features`, spelled as the member's path (`insert_options.defer_defaults`). A reader treats an absent reserved output member as not reported. `gen.py` checks only that this rule is stated.

The description is locked: its `stability` is `locked` (public issue #511 records the lock). Locking it moved the fingerprint one last time, so a released 2.0.0 SDK never accepts a dev build and a dev SDK never accepts a 2.0.0 library. SDK 2.0.0 ships from the production `chtypes/v2` repository, signed with the release key.

## Preamble

This header is generated from `spec/abi-v2/abi.json` by `scripts/abi-v1/gen.py --major 2`. Edit the description and regenerate; never edit this file. `docs/reference/abi-v2.md` is the normative reference, and the rules generation 2 is written under (r1 to r9) are in it.

Stability. Generation 2 is locked: `CHS_ABI_FINGERPRINT` is fixed, and the description evolves only by reserve and decline (rule r9). SDK 2.0.0 and later speak it and fetch from the production `chtypes/v2` repository, signed with the release key; the pre-release SDKs (`2.0.0-dev.N`) spoke its unstable drafts, and a library built from a draft is refused by its fingerprint. ABI v1 (`include/chtypes.h`) is frozen and unaffected.

Identity. `CHS_ABI_VERSION` is the generation and `CHS_ABI_FINGERPRINT` is sha256 over the canonical form of the description. A loader opens a library with `RTLD_NOW | RTLD_LOCAL`, calls only the handshake set (`chs_abi_version`, `chs_build_info`, `chs_clickhouse_version`) before its checks pass, and refuses any library whose generation or fingerprint differs from the ones it was compiled with. Nothing degrades: every described symbol is mandatory.

Ownership. Every input string, statement, document and body is counted bytes, `(const uint8_t *p, size_t n)`: length 0 is none and the pointer may then be NULL, and a NULL pointer with a nonzero length is `CHS_INVALID_ARGUMENT`. Every output is an owned, opaque `chs_buf`, read with `chs_buf_data` and `chs_buf_len` and released with `chs_buf_free`. Bytes pass through unmodified, NUL and invalid UTF-8 included: a column name may contain either (measured on live servers), so no name, statement or message is ever a C string. The only static strings are the handshake's. Handles are opaque, reference-counted and tagged with their kind and the image that made them; every entry point checks both, a child holds a strong reference to what it needs, and each free drops only the caller's reference, so any free order is safe and freeing NULL does nothing.

Errors. A fallible call returns a `chs_status` and, through an optional last `chs_error **err`, an owned error carrying the status, ClickHouse's own code and name, the message, the column and, for a decline or a library-side refusal, the reason: the catalog id (`chs_error_reason`, `spec/abi-v2/declines/declines.json`) a caller keys on instead of matching message text. The status alone carries the verdict, so `err` may be NULL.

Codes. One code space serves the error and every document's `code` and `verdict_code`: a positive value is ClickHouse's own error code, as the server's table names it; `CHS_CODE_DECLINED` (-2) is this build's decline; and 0 is written only on a success (`accepted`, `accepted_poisoned`, `ok`, a `t` or `f` verdict). A refused or declined row, outcome or verdict never carries 0, and no other negative or library-private number is ever written. Every decline and library-side refusal also names its reason, the catalog id, in the error and in the document (`reason`, `verdict_reason`), and ids and the sentinel are stable once published (rule r4). A message is informative: a caller keys on the status, the code and the reason, never on message text. Exact text is guaranteed only where this description quotes it: the decline of a member this build does not implement (Input documents, reason `option-not-implemented`), an `ATTACH TABLE` statement under `create` (`chs_schema_create`), and a dev SDK's fingerprint refusal (rule r6). No other message text is normative, the pinned texts of generation 2's earlier drafts included.

Conditional members. A document's schema states the members it always carries (`required`). These members are present under a condition the schema cannot see, and each condition is a MUST on the library, held by a conformance case in the SDK's suites (named in brackets) that drives it both ways; a binding MAY check them and, when it does, fails closed on a violation.

- **The export.** When `chs_preview_batch` is asked for an export (`export_format` is not `CHS_EXPORT_NONE`), exactly one of `export_declined` and `row_spans` is present; with `export_declined`, `export_declined_reason`, its catalog id; and with `row_spans`, `export_columns`; with no export asked for, none of them is [`batch.export_members_xor`].
- **The filter.** A row's `verdict`, `verdict_code` and `verdict_err`, and the batch's `rows_passed` and `rows_cut`, are present exactly when the call carries a filter (`chs_preview_batch` with a non-NULL `filter`) [`batch.verdict_iff_filter`].
- **The reason.** `reason` is present exactly where its `code` is `CHS_CODE_DECLINED` (a row, a batch, a filter result, an `errors[]` entry), and `verdict_reason` exactly where its `verdict_code` is [`doc.reason_iff_declined`].
- **The site.** `refused_at` is present exactly when the outcome of a batch, a filter result or `chs_preview_row`'s row is a refusal or a decline (`rejected` or `unsupported`), and never for `accepted`, `accepted_poisoned`, `skipped` or `ok`; `refused_row` is present exactly when `refused_at` is `row`, and on a batch or a filter result it is less than `rows_read`. The rows of a batch carry neither: the batch's own say where [`doc.refused_at_iff_refused`].
- **The verdicts.** A filter result's `verdicts` has exactly `rows_read` characters [`filter.verdicts_len_is_rows_read`].

Threads. Every function has a thread class, listed in the reference. A handle is immutable once made, so every call that only reads handles is `shared`: any number of threads may call it at once, on the same handles too. The one thing a caller must never overlap with a call is a free of a handle that call uses. Process setup (`chs_initialize`, then `chs_set_defaults`) runs before the traffic it configures.

Initialization. Every function has an init class, listed in the reference and in its own comment: `any`, valid before and after `chs_initialize`; or `required`, valid only once `chs_initialize` has succeeded. Until then a `required` call changes nothing and returns `CHS_INVALID_ARGUMENT`, ch_code 0, and when its arguments are otherwise valid its message starts `<function>: call chs_initialize first`; it never crashes. The `any` calls are the handshake and the tombstone, `chs_initialize`, `chs_shutdown`, the error and buffer accessors, and every free. Each of them but `chs_initialize` returns no `chs_status`, so it has nothing to refuse with. The error and buffer accessors read the refusal itself (`chs_error_message` returns a `chs_buf`), and a free given NULL does nothing, which is all a server, schema, filter or block free can be given before `chs_initialize`, because nothing makes one. Every other call is `required`, unless its own section says it is valid before `chs_initialize`.

Stacks. A call's answer doesn't depend on the calling thread's stack. Every call that returns a `chs_status` runs with an 8 MiB stack's worth of room: on the calling thread when half its stack, less what it has used, is between 3.75 MiB and 4 MiB (a default 8 MiB thread: glibc's, a Go cgo call, a Python thread, a main thread); otherwise on a library-owned thread with an 8 MiB stack, one per calling thread, made at its first such call and ended with it. The caller blocks until the call returns. The library's threads block every asynchronous signal. After `fork()`, a child's first such call makes its own thread. If the library can't make its thread, the call returns `CHS_INTERNAL`. The frees, the buffer and error accessors, `chs_shutdown` and the handshake always run on the calling thread.

Time zones. A library image has one zone of its own, set once by `chs_initialize`: the image zone. A schema has a home zone, the zone its server binds: the `session_timezone` in its server's `settings` (`chs_server_create`) when that is set, else its server's `timezone`, else the image zone, in both postures. The schema's types bind its home zone, as a server's table binds the server's zone after a restart (measured on a 26.8 server whose `timezone` and whose profile's `session_timezone` differ: its zone-less types bind the `session_timezone`), and so do the functions its DEFAULT, MATERIALIZED, ALIAS and CHECK expressions apply to its columns, its PARTITION BY expressions, and a Date-valued TTL under a merge. Each call runs in a zone too, the first of these that is set: the call's own `session_timezone` (a key in its settings, which ClickHouse applies through its own query context); the `session_timezone` in the schema's own settings; the one in its server's `settings`; the one set by `chs_set_defaults`; its server's `timezone`; the image zone. An empty `session_timezone` at any of these means the server's own `timezone`, else the image zone (the last two), never the profile's `session_timezone` or the home zone: a call naming `''` reads and renders in the server's `timezone` while the schema's bound types keep the home zone. The call's zone governs parsing and rendering a zone-less `DateTime` or `DateTime64`, export, a DEFAULT literal's fold, `toDateTimeOrZero` and a filter's literals. A `Date` partition id is the civil date in every zone. Every zone name is validated by ClickHouse's own `DateLUT`, which reads the library host's time zone database, on every platform. On darwin the file system is case-insensitive, so `DateLUT` there accepts a spelling such as `utc` that a Linux server refuses; that difference is documented, not patched.

Settings. Every settings input is a JSON object whose values are JSON strings, or the object form for bytes (Input values, below), and a binding never rewrites one. A call's settings are layered, highest first: the call's own `settings`; the schema's own (`chs_schema_create`); its server's `settings` (`chs_server_create`); the defaults set by `chs_set_defaults`; the build's own. A filter's WHERE takes the same layers, lowest first: the build's own, `chs_set_defaults`, the server profile, the schema's own, and the filter's own (`chs_filter_create`), with `session_timezone` at every layer staying on the zone path (Time zones, above). One exception: a type gate in the schema's own settings binds the CREATE only, and a WHERE's CAST validates under the session layers, every layer but the schema's own. At the INSERT, the schema's own settings reach only the parse, as a server's CREATE-time settings never reach its INSERT: the settings ClickHouse's own `FormatFactory::getFormatSettings` reads, which shape how a body is read, keep all five layers, except a type gate among them (`Nullable(Tuple)`'s, for one), which binds the CREATE only. Everything else the INSERT does runs under the call's own settings, its server's `settings` and `chs_set_defaults` only, over the build's own, with every type gate at the build's default unless one of those three sets it. That covers every expression it evaluates (a `DEFAULT` or `MATERIALIZED` fill, a `CHECK`, a TTL, a partition key the server rebuilds at INSERT, one with a modulo, a projection, an expression a `Values` body evaluates while it is read, and the creator of any aggregate function in them) and its limits, `max_partitions_per_insert_block` and `throw_on_max_partitions_per_insert_block` among them. The sorting key and the skip indices, which a server builds under its global context, run under its server's `settings` and `chs_set_defaults` only, though an aggregate function's creator there still reads the call's own settings. So a gated `CAST` or a gated aggregate function in such an expression, a `Values` body's included, with its gate only in the schema's own settings, is refused as the server refuses it (455, 44 or 63), and a partition limit in the schema's own settings does not reach the INSERT; a caller whose real INSERT session carries such a setting passes it in the call's settings or the server profile, as that INSERT does. `session_timezone` keeps the zone path. Each setting that reaches a WHERE is honored (applied to it), passed through (accepted and ignored), or declined (`chs_filter_create` says how). A server resource limit (an `execution`-tier setting, e.g. a small `max_columns_to_read`) can make the server refuse a query the library answers; that is resource policy, not row access, and the library does not model it. A server's settings are the ones its profile applies to every query. At posture `create`, they are layered under the schema's own settings for the whole CREATE, so they shape how the schema compiles (`flatten_nested`, the type gates and the aggregate gates among them). At posture `load`, the stored definition is taken as written, as a server attaches it at startup. No call reads a server's version or its changed settings itself: that discovery is a recorded gap in this generation, so a caller that wants a server's settings passes them explicitly, in a server profile, through `chs_set_defaults` or in each call's settings.

Documents. Every output document is valid JSON that a stock parser reads: every ClickHouse rendering (a stored value, an input value, an engine's row) is a JSON string, a number written bare is within plus or minus 2^53 (anything larger is a string), and there is never a bare `inf`, `-inf` or `nan`. Every column entry of a row carries `null`, the library's verdict that the stored value is NULL, poisoned cells included.

Byte strings in JSON. Every data-derived string a JSON document carries is a byte string: a column name, a value's rendering, a type (an Enum label or a named Tuple element comes from the caller's DDL), SQL text, and a message (ClickHouse's messages quote input bytes). One rule carries them all, names included, in every output document and in the input column list. The member `F` is a JSON string when the bytes are valid UTF-8, a NUL written as the escape `\u0000` as RFC 8259 allows. Otherwise the member `F_b64` holds the raw bytes in standard base64, padded. The two are never both present, and a member that names an entry (a column name) is always present in one of its two forms. So every document is valid UTF-8 JSON that a strict parser reads, and no byte is lost or replaced. Where a list or a map would hold a bare data-derived string, it holds an object instead, so the rule applies to that object's members: a list of names is a list of `{name}` or `{name_b64}` objects, and an engine's row is a list of cells. Each document lists its data-derived fields (`byte_fields` in the reference); a binding decodes each one to bytes and never assumes UTF-8. A server accepts every kind of name (measured on every supported line). The byte-returning accessors (`chs_error_message`, `chs_error_column`, `chs_error_ch_name`) and the export bytes are raw buffers, not JSON, and are not affected.

String values. Every entry that reports a stored value (a row's `cols`, `computed`, an engine row's cells, `storage_transforms`) carries `stored` or `stored_b64`, which is always ClickHouse's rendering of the value. For a scalar `String` or `FixedString` value, including one inside `Nullable` or `LowCardinality`, the entry also carries `value_b64`, the value's raw bytes in standard base64, whenever the value is not NULL, whether or not the bytes are valid UTF-8. A value nested in another type (`Array(String)`, `Map`, `Tuple`, and the like) carries no `value_b64`: that is a recorded gap in this generation, and its rendering is the only form.

Input values. A value in a settings or query-parameters input (every `settings` and `query_params`, and a server profile's `settings`: the content `json_object_byte_values`) is a JSON string when its bytes are valid UTF-8, and otherwise the object `{"b64": "<standard base64, padded>"}`, which carries the raw bytes: `{"format_csv_delimiter": {"b64": "/w=="}}` sets the one byte 0xFF. It is never a `<key>_b64` member, which could collide with a real key. The two forms are the same value when the bytes are valid UTF-8, so a binding may send either, and it MUST send the object form for any other value. Any other object, and a value of any other JSON type, is `CHS_INVALID_ARGUMENT`, naming the key. A key never takes the object form: setting and query-parameter names are ClickHouse identifiers. Every JSON input is valid UTF-8 JSON (RFC 8259), so a raw byte that is not UTF-8 inside a JSON string is `CHS_INVALID_ARGUMENT`, and the object form is the one way to carry such a value. The other inputs take no object form: an options document's values are closed vocabularies, a server profile's `timezone` and `macros` are names a server's configuration spells, and the input column list carries a name that is not UTF-8 as `name_b64`, by the rule for byte strings in JSON.

Input documents. A counted input whose content is `input:<name>` is a JSON object that the library validates against the document of that name (rule r1). A key the document does not define is `CHS_INVALID_ARGUMENT`, naming the key, and so is a document that is not a JSON object or a member of the wrong JSON type. Length 0 is `{}`, and a repeated member keeps its last value. The library never ignores a key, so a caller that sets an option a build does not implement is told so instead of silently getting the old behavior. The whole document is validated before any member is acted on, so a document with a key it does not define is `CHS_INVALID_ARGUMENT` even when it also sets a member this build declines. A member a document defines but this build does not implement, set to any value but its default, is `CHS_DECLINED` with ch_code 0 and exactly the message `<function>: <document> sets <member> to "<value>", which this build does not implement; declined rather than answered` (for example `chs_preview_batch: insert_options sets verdict_basis to "export", which this build does not implement; declined rather than answered`), reason `option-not-implemented`, which is never a wrong answer. At a call that answers with a document (`chs_preview_row`, `chs_preview_batch`, `chs_filter_eval_body`, `chs_block_create` and `chs_filter_eval_block`), that decline is the document's, not a status: outcome `unsupported`, `code` `CHS_CODE_DECLINED`, `refused_at` `call` and `reason` `option-not-implemented`, with the status `CHS_OK` (`refusal_site`).

Teardown. `chs_shutdown` stops what `chs_initialize` started. A loader never unloads a library: unloading or initializing an image again in one process is unsupported. Before `chs_initialize`, every call that returns a `chs_status`, other than `chs_initialize` itself, refuses with `CHS_INVALID_ARGUMENT` and ClickHouse code 0, naming the call, and leaves its out-parameters NULL. After `chs_shutdown` has run, every such call refuses the same way, its message saying that `chs_shutdown` has run. The handshake, `chs_abi_revision`, `chs_shutdown`, the buffer and error accessors and the frees answer at any time.

Images. Any number of library images, one per ClickHouse line, may be loaded and used concurrently in one process, from any number of threads, each initialized once with its own zone, and every answer is the one a single image on a single thread gives. The one exception is the admission time budget (`chs_set_defaults`): it measures the evaluating thread's CPU time, and an evaluation that costs more than about half of the budget on an idle core may be declined (`CHS_CODE_DECLINED`, reason `admission-time-budget`) when the process's load raises its CPU time, never answered differently: above the budget on an idle core it always declines, below about half of it never. Its catalog entry states this load dependence. A conformance case drives two lines, then four, concurrently in one process.

### chs_buf

An owned, immutable byte buffer: every output of the library. Read it with `chs_buf_data` and `chs_buf_len`; the bytes are exactly what the library produced, with no terminator and no encoding promise beyond what the producing parameter's content says.

### chs_error

The error a fallible call reports when its status is not `CHS_OK`: the status, ClickHouse's own error code and name, a message and the column concerned. Created only by the library, through a call's `err` out-parameter.

### chs_server

One ClickHouse server, as a profile describes it: its `timezone`, the settings its profile applies to every query, and its `<macros>`. Immutable once created, so any number of threads may use it at once. A schema created on it holds a counted reference to it, so the caller may free the server whenever it likes.

### chs_schema

A compiled table: the columns, engine, keys, TTL, settings and constraints of exactly one `CREATE TABLE` statement, on the server it was created on, if any. Immutable once created, so any number of threads may use it at once.

### chs_filter

A compiled boolean SQL expression over a schema's columns, with its query parameters bound. It holds a counted reference to its schema, so the schema stays alive for as long as the filter does, whatever order the caller frees them in.

### chs_block

A body parsed once under a schema, for evaluating many filters without parsing again. Like a filter, it holds a counted reference to its schema.

### chs_status

The verdict of every fallible call, in five values whose numbering is frozen.

- `CHS_OK`: the call succeeded and its outputs are set.
- `CHS_REJECTED`: ClickHouse's own refusal, with its own code, name and message, which a server would also give. `CHS_REJECTED` with ch_code 306, TOO_DEEP_RECURSION, never `CHS_INTERNAL`, is returned for a deep argument the call compiles (an expression, a type, or a settings, columns or options JSON), at `chs_set_defaults`, `chs_server_create`, `chs_schema_create`, `chs_filter_create`, `chs_type_validate`, `chs_reference_type` and `chs_discover_columns`. A call that answers with a document (`chs_preview_row`, `chs_preview_batch`, `chs_filter_eval_body`, `chs_block_create` and `chs_filter_eval_block`) returns a status other than `CHS_OK` only for caller misuse (`CHS_INVALID_ARGUMENT`) or a library bug (`CHS_INTERNAL`): every refusal or decline of the call itself, of its settings, its column list or its options, a deep argument (306) included, is reported in its document with `refused_at` `call`, and a body's refusal with `refused_at` `row` or `body_step`, as every refused body is. `chs_schema_describe` never refuses a schema `chs_schema_create` returned: the statement's depth is judged at compile.
- `CHS_DECLINED`: this build will not answer; a server might accept. Never scored as agreement. The error names the reason (`chs_error_reason`). A call that answers with a document never returns it: its decline is the document's `unsupported` with `refused_at` `call`.
- `CHS_INVALID_ARGUMENT`: caller misuse, such as a NULL pointer with a nonzero length, a wrong-kind, freed or cross-library handle, or a NULL required out-parameter.
- `CHS_INTERNAL`: a guarded exception inside the library, which is a library bug.

The set is closed within this generation: any new condition maps onto one of these five. A binding maps each status to one error class (`spec/abi-v2/sdk.json`), and treats a value outside the set as an internal error naming it, whose status is that value's `unknown(n)` (rule r3).

### chs_format

The input and export formats, numbered as they have been since the first release; the numbers are frozen and a binding passes the integer. `ch_name` is ClickHouse's own name for the format, which is how `chs_build_info` lists the formats a build supports. Being in this enum never proves a build supports a format: the build says so in its `capabilities`.

### transform_reason

The reason a stored value differs from the supplied one, as the library reports it per column. `lossy` says whether information was lost; exactly four reasons are lossless (a representation change, a value filled from a DEFAULT or the type's zero, and a DEFAULT the library resolved from its own clock), and they are still reported because a preview must show what the table will hold. A binding reads `lossy` from here and never keeps a list of its own.

### merge_reason

What a merge would do to one row of the part an `INSERT` writes, as the batch document's `at_merge` reports it: `ttl_delete`, the table's rows TTL removes the row; `ttl_column_reset`, a column's TTL resets the column's value. A reason added later is a new value, which a reader reads as its `unknown(n)` (rule r3).

### default_kind

A column's default kind, as ClickHouse names it: `DEFAULT`, `MATERIALIZED`, `ALIAS` or `EPHEMERAL`, or the empty string for a column with none. The schema description carries one per column.

### default_support

What this build does with a column's DEFAULT, as `schema_description` reports it per column (reserved: a build that does not report it writes no `default_support`): `computed`, the library evaluates the expression itself (a literal, a deterministic expression of the row, an admitted clock read); `generated`, the library draws the value with an admitted generator (`default_generated`); `deferred`, the library cannot compute it and `insert_options`' `defer_defaults` `server` would defer it; `declined`, the library cannot compute it, so a body that omits the column is declined, with the catalog id in `default_support_reason`. The honor set behind it is published per line as data beside `where-settings/<line>.json`. A value added later is a new value, which a reader reads as its `unknown(n)` (rule r3).

### declined_tier

The tier of a setting a settings layer sets and this build's filters do not honor in a WHERE, as `schema_description`'s `filter_declined_settings` reports it, spelled as this build line's WHERE-settings list (`spec/abi-v2/where-settings/<line>.json`) spells it: `predicate` (measured to change a verdict), `predicate-unflipped` (read in the WHERE's scope, though no value the flip test tried changed a verdict) `result-content` (selects rows by content), or `server-refuses` (a cell of `where-settings/documented-pathological.tsv`: a value under which the server refuses every query, so no row verdict can stand). The lists' other tiers (`execution`, `result-truncate` and `output`) never appear here: those settings are passed through and ignored. A tier added later is a new value, which a reader reads as its `unknown(n)` (rule r3).

### declined_layer

The settings layer a `schema_description` `filter_declined_settings` entry comes from, the highest one that sets the name: `defaults` (the defaults `chs_set_defaults` set, as `chs_schema_create` captured them), `server` (the server profile's `settings`, `chs_server_create`) or `schema` (`chs_schema_create`'s own `settings`). The values are in layer order, lowest first, which is the list's order. A layer added later is a new value, which a reader reads as its `unknown(n)` (rule r3).

### posture

How `chs_schema_create` compiles its statement, as `schema_options`' `posture` asks and `schema_description` reports: `create`, as a server runs a `CREATE TABLE` (ClickHouse's `LoadingStrictnessLevel::CREATE`), the default; `load`, as a server loads the stored definition of a table it already holds when it starts (`LoadingStrictnessLevel::FORCE_ATTACH`). `schema_description` carries the member only for `load`: absent is `create`. A posture added later is a new value, which a reader reads as its `unknown(n)` (rule r3).

### refusal_site

Where a refusal or decline sits, as `refused_at` reports it on a batch document, a filter result and `chs_preview_row`'s row whenever the outcome is `rejected` or `unsupported` (Conditional members, in the Preamble): `call`, the call itself (its settings, its column list, its options, or a decline of the call such as a zone mismatch), before a byte of the body was read; `body_read`, the body outside any row and before the whole-body steps, so no record is to blame: a header the format reads first (a `WithNames` or `WithNamesAndTypes` header line, a header field naming a column the INSERT does not list under `input_format_skip_unknown_fields` 0), the framing (a JSON array's brackets, a separator or trailing content after the last record) or a byte-order mark the reader refuses; `row`, one row of the body, whose index is `refused_row`; `body_step`, a whole-body step over rows the parse accepted (the partition split, the writer's index expressions, the engine merge, the TTL, the projections, a CHECK over a merged block). `refused_row` is present exactly for `row`. A site added later is a new value, which a reader reads as its `unknown(n)` (rule r3).

### discover_query_param

The query parameters in the SQL `chs_discover_query` returns, each with its ClickHouse type. The caller binds them when it runs the query (over HTTP, as `param_database` and `param_table`), so no binding builds SQL.

### value_src

Where a column's value came from. `is_stored` says whether the row as stored carries a value for the column: a column the input named but the table never stores (an EPHEMERAL column, a skipped MATERIALIZED or ALIAS column) and a DEFAULT the library could not resolve carry none. A source this description does not list reports its fallback's facts, `skipped`'s: `is_stored` false (rule r3).

`default_generated` marks a DEFAULT column whose expression calls a random or ID generator the build admits; a build that does this lists `default_generators` in `chs_build_info`'s `capabilities.features`. The label means: generated by chtypes, and it becomes the stored value when you insert this output. The library drew the value itself, with ClickHouse's own vendored function. So insert the library's output (the export of `chs_preview_batch`, or the stored values its documents report), not your original input: a server evaluates a DEFAULT only for a column the INSERT does not supply, and the original input, which omits the column, would make the server draw a different value. Generators are admitted only in DEFAULT expressions: a MATERIALIZED column is always computed by the server, and an EPHEMERAL column is not stored. No binding logic is involved; a binding reports the source as it reads it.

`default_override` marks a column whose value came from `insert_options`' `column_defaults`: the caller's value in a cell the server would have filled from the column's DEFAULT. It is stored, and the export carries it as a present value. A build that does not implement `column_defaults` never writes it.

`default_deferred` marks a DEFAULT column the call deferred to the server (`insert_options`' `defer_defaults`): the library computed no value, the export omits the column from every line and from the batch document's `export_columns` (a body whose rows do not all defer it is declined: `defer_defaults`), and the server fills it on INSERT. A build that does not implement `defer_defaults` never writes it.

### row_outcome

The verdict on one row: accepted, accepted but unreadable afterwards (the insert succeeds and every later read fails), rejected, skipped under the server's error allowance with the batch continuing, or declined by this build.

### batch_outcome

The verdict on a whole body. A batch is never skipped; its rows carry their own outcomes.

The batch answers the first of these that applies:

1. **A call-level rejection is `rejected`.** The call's own settings are refused (a value the settings constraints or the setter refuse), or the INSERT column list's verdict, a CREATE-time type gate or a contract violation refuses the call. The server refuses these before it reads a byte of the body, so no row changes the answer.
2. **A call-level decline is `unsupported`,** with the setting named in the batch document's top-level `unsupported_settings`. This holds whatever the rows say, refusing rows and an empty body included: every row was read in a context the call did not ask for, so neither an acceptance nor a refusal there is the server's answer (a DateTime past the type's range in the schema's own zone can be in range in the call's zone). Every row reads `unsupported`, filter rows read `d`, the row preview answers the same, and no export bytes are produced.
3. **Otherwise the first row, in body order, that is neither accepted nor skipped** gives its outcome (`rejected` or `unsupported`) and its code. An `unsupported` row ends the read, so a refused row after it is not reached and the batch stays `unsupported`. After the rows, the whole-body steps run in the server's order (the Object and Dynamic block steps, the DEFAULT step over the reader's chunks, the partition split, the writer's index expressions, the engine merge, the TTL, the projections), only on a batch the rows left accepted, and each may still refuse or decline it.
4. **`accepted_poisoned`:** a stored value the server itself cannot read back. The INSERT succeeds, but nothing is exported.
5. **`accepted`,** the only verdict that exports bytes.

A skipped row never changes the verdict. Steps 2 and 3 depart from "rejected if any row is refused" for one reason: never a refusal that is not definite. Both answer `unsupported`, which a caller never scores as agreement.

A filter's verdicts follow the batch. When the batch's outcome is not `accepted`, by any of steps 1 to 4, every row's filter verdict is `d`. A row the parse accepted carries `verdict_code` -2, its `verdict_reason`, and `verdict_err` `batch outcome is '<outcome>': only a fully accepted batch has filter verdicts`; a refused row carries its own code and message. Nothing from such a batch is stored for a WHERE to read, exported or counted, so no verdict of it is an answer.

### filter_outcome

Whether a filter evaluation answers its body. `ok`: every row carries its own verdict, and per-row failures are verdicts, not outcomes. Under any non-`ok` outcome, including `unsupported`, the library writes `d` for every verdict, on `chs_filter_eval_body` and `chs_filter_eval_block` alike, so the rule holds in the data; a caller MUST still treat every verdict as `d` whatever the verdict string holds. The document's `refused_at`, `refused_row` and `reason` say where the refusal sits and why.

`chs_filter_eval_body` and `chs_filter_eval_block` answer `ok` only for a body a server would accept, that is, when `chs_preview_batch`'s verdict over the same body, settings and column list, with no filter, is `accepted`. Otherwise the outcome mirrors that verdict: `rejected` with its code and message; `unsupported` with its code and message, a call-level decline included; and `unsupported` with code -2 for `accepted_poisoned`, which this vocabulary does not hold and which is no refusal of the INSERT. A body the parse itself refuses answers `rejected` or `unsupported`, with a `d` for each record read (`rows_read`, 0 when nothing was read).

### filter_verdict

One character per row of a filter evaluation. `t` and `f` are answers (true; false or NULL); `e` (the predicate raised an error on this row) and `d` (this build declines the row) are not, and a caller enforcing visibility must fail closed on both. A verdict is an answer only for a body a server would accept: in a batch whose outcome is not `accepted` every verdict is `d`, and in a filter document whose outcome is not `ok` (any non-`ok` outcome, including `unsupported`) a caller MUST treat every verdict as `d` (`batch_outcome`, `filter_outcome`).

**What a filter verdict is.** A filter verdict answers one question per row: would a ClickHouse server of the pinned version, on the same OS and architecture, return this row from `SELECT … FROM <table> WHERE <filter>`, if the table held exactly the row this INSERT would store? It is the server's `WHERE` over that one row, as the table stores it and the server reads it back.

- **`t`:** that query returns the row. Truth follows the server's own `WHERE` rule: a non-zero number keeps the row, and NULL never does. A `t` is a security claim. A `t` where the server would not return the row is an over-accept, a security-severity defect.
- **`f`:** the predicate is false or NULL, so the query does not return the row.
- **`e`:** the predicate threw on this row's values. The verdict carries the server's own code and message. A server fails the whole query in that case, because a `SELECT` has no per-row error channel.
- **`d`:** the library declines to answer for this row because it cannot be sure the server would answer the same. Examples:
  - the row cannot be stored;
  - the filter reads a value the server computes for itself, such as a clock read or a generator;
  - the call carries a setting the library cannot honor;
  - the filter has a shape on the decline list.

A caller that authorizes rows with filters treats anything but a definite `t` as no: `f`, `e`, `d` and `unknown(n)` all mean no.

**What the model leaves out, by design:**

- **Other rows.** A verdict does not depend on which other rows the table holds. If the predicate throws on a different row of the same part, a real query fails as a whole, but this row's verdict is unchanged: each row carries its own `t`, `f` or `e`.
- **What storage does later.** Engine merges, TTL expiry, mutations and deletes change what the table holds over time. The verdict is the `WHERE` over the record as stored by this INSERT.
- **Other query shapes.** A planning refusal that only another query shape reaches is not a row verdict; an example on some versions is an aggregate `SELECT count() … WHERE`. Where the row shape itself reaches such a refusal, the library declines the filter (`d`).
- **The server's platform.** The library answers for a server on its own OS and architecture. On 26.3, ClickHouse's own parse of Float values from text input formats differs across macOS, Linux amd64 and Linux arm64 (mostly one ULP), so stored Float values, and comparisons involving them, can differ between servers of different architectures. Run the library on the server's platform; on 26.7 and later, every platform agrees.

**A body the INSERT does not accept has no filter verdicts** (`batch_outcome`, `filter_outcome`). Any outcome other than `accepted` (a batch) or `ok` (a filter document) means every verdict is `d`.

### document:schema_description

A schema's columns, in declared order, with each column's canonical type, its `default_kind` (a value of the `default_kind` vocabulary) and default expression, and the facts a caller needs to build a row. The document is `{"columns": [...]}`, and each entry carries `name`, `type` and `default_kind` (a value of the `default_kind` vocabulary), always, and `default_expression` (empty when there is none) and `default_is_literal`; the name, the type and the expression follow the rule for byte strings in JSON. `type` is present on every column: a column whose type the compile cannot settle (a column declared without a type whose own DEFAULT or ALIAS this build cannot type) is declined by `chs_schema_create` (`CHS_DECLINED`, reason `column-type-unsettled`), so no schema describes a column without its type. The decline is a limit of this build, never a claim about whether a server accepts the table. `default_support`, a `default_support` value with `default_support_reason` for `declined`, says what this build does with the column's DEFAULT; reserved, absent until a build writes it. `reads`, a list of name objects, names the columns the column's DEFAULT, MATERIALIZED, ALIAS or EPHEMERAL expression reads, as ClickHouse's own analysis of the expression's required source columns reports them, each once, in the table's declaration order: a build that writes it writes it on every column, `[]` for a column with no expression or one that reads none. Reserved (rule r9): absent until a build writes it, which that build advertises in `chs_build_info`'s `capabilities.features`; a reader treats it as not reported until then. A schema `chs_schema_create` returned always describes: the walk describing needs runs at compile, so a compiled schema is never refused here.

`posture`, a `posture` value, is present only on a schema compiled in a posture other than `create`, so the document of a schema compiled in `create` is byte for byte what it was before postures existed.

Two members report the server a schema was created on. Both are absent on a schema created with `server` NULL, so that document is byte for byte what it was before servers existed.

- `server`, on every schema created on a server, even one described by `{}`: `timezone` is the zone the schema's types bind (the profile's, or else the image zone, exactly as `chs_initialize` spelled it), so a reader never needs the image zone separately; `settings` is the server's settings as the profile gave them, `{}` when it gave none; `macros` is the server's macro set as the library holds it, present exactly when the profile carried `macros`. These are the caller's own values given back, not data-derived, so the rule for byte strings in JSON does not apply to them: the zone and the macros are plain strings, and each settings value is a JSON string when its bytes are valid UTF-8 and otherwise the object form `{"b64": …}` (Input values), so a settings value takes the object form only when its bytes are not UTF-8. The member no longer carries `filter_declined_settings`: that list is the top-level one, below, over every layer.
- `replicated`, on a schema created on a server whose engine is a Replicated one: `zookeeper_path` and `replica_name`, the path and the replica name ClickHouse's own `TableZnodeInfo` resolved, fully expanded. The database and table names expanded into them are DDL bytes, so both follow the rule for byte strings in JSON. A caller can compare them with the server's own `system.replicas`.

`filter_declined_settings` is required on every schema description, with or without a server: an array, `[]` when nothing is declined. It lists the settings the schema compiles under that this build's filters do not honor in a WHERE, over every layer known when `chs_schema_create` ran, and `chs_schema_create` computes it. The layers, lowest first, are the `declined_layer` values:

- `defaults`: the defaults `chs_set_defaults` set, as `chs_schema_create` captured them. This is the snapshot the schema compiles under, never a later call (which the latch refuses anyway once a schema exists).
- `server`: the server profile's `settings` (`chs_server_create`), when the schema was created on a server.
- `schema`: `chs_schema_create`'s own `settings`.

Each entry is `{name, tier, layer}`: `name` follows the rule for byte strings in JSON (`name` or `name_b64`), `tier` is a `declined_tier` value, the tier this build line's WHERE-settings list gives the name, and `layer` is a `declined_layer` value. The entries are:

- every name set at any of the three layers that the line's list carries at tier `predicate` or `predicate-unflipped` and that is not in this build's honor set (the settings it applies to a WHERE, each with a measured case where the server's verdict moves and the library's tracks it);
- `compatibility`, at tier `predicate`, when its value at the highest layer that sets it moves a listed setting outside the honor set;
- every `result-content` name set at any of the three layers, honored or not: a setting that selects rows by content beyond the WHERE is outside a row verdict's scope whatever the library applies;
- every cell of the line's `where-settings/documented-pathological.tsv` present at any of the three layers, at tier `server-refuses`: the server refuses every query under that value, so no row verdict stands.

So the consumer rule is one check: refuse when the list is not empty. No consumer copies the WHERE-settings lists or the pathological cells.

A name the list does not carry is never an entry, and neither is a setting of the `execution`, `result-truncate` or `output` tiers: those are passed through and ignored. The test is presence, not value: any value at any layer counts, a declined name set to its default value included, because some of ClickHouse's reads are `isChanged()`, which asks only whether a setting was set. A higher layer that sets the same name never takes the entry away; it only moves the entry's `layer`.

The order is deterministic. There is one entry per name, at the highest layer that sets it (`defaults`, then `server`, then `schema`). The entries are ordered by layer, `defaults` first, and within a layer by name as raw bytes, ascending; a `name_b64` entry sorts by its decoded bytes.

The list holds only the layers known at schema compile. A filter's own `settings` (`chs_filter_create`) are never in it: a declined one there is named at evaluation (`filter_result`'s `unsupported_settings`, every verdict `d`), and a cell of `documented-pathological.tsv` there declines `chs_filter_create` itself (`setting-server-refuses`). The settings an evaluation brings (the call's, and the body's) are never in it either: they govern parsing the body and never reach the WHERE, so they are never named as WHERE settings (`chs_filter_create`). A schema whose list is not empty is one `chs_filter_create` declines.

### document:row

One row's verdict and, as the flags ask, its columns' stored values, provenance and transformations. `outcome` (a `row_outcome` value), `code` (Codes, in the Preamble) and `input_span` are always present, `err` names the refusal, and `reason` the catalog id of a decline. With a filter attached (`chs_preview_batch`), `verdict` (a `filter_verdict` value), `verdict_code`, `verdict_err` and, for `d`, `verdict_reason` are present on every row; with none they are absent. On `chs_preview_row`'s document, which stands for the whole call, `refused_at` and `refused_row` say where a refusal sits (`refusal_site`); the rows of a batch carry neither. Every entry of `cols` carries its name, `null` (whether the stored value is NULL, poisoned cells included), `src` (a `value_src` value), its renderings (`input`, `stored`, `ref`, `wire`) and its types (`type`, `base`, `ref_type`), all by the rule for byte strings in JSON, `value_b64` for a String or FixedString value, and the booleans `nullable` (the column's type is Nullable), `poison` (the stored value is one the server cannot read back), `null_input` (the input field was the format's NULL literal) and `dup_dropped` (a duplicate key the reader dropped), with `ref_unclassified` present, true, when the reference type could not be classified. `unknown_fields` is a list of name objects (the call's declined settings are the batch document's `unsupported_settings` only, which every row of the batch shares); `computed` entries carry a name, a `kind` (the column's default kind, lower case) and a stored value; `err`, `verdict_err` and `partition_id` follow the rule too. The transformations come from the library, never from a binding: each is the `transformed` entry the SDK's parity fixtures pin, with its `reason` from `transform_reason` and its `lossy` fact. `input_span` is `{off, len}`, the bytes of the input body the reader consumed for this record, read from the vendored reader's own position. A `rejected` row always carries a nonzero ClickHouse code, and an `unsupported` one `CHS_CODE_DECLINED` with its `reason`.

### document:batch

A body's verdict, counts and per-row documents, and, when an export ran, where each row sits in the export bytes. Always present: `outcome` (a `batch_outcome` value), `code` (Codes, in the Preamble), `err`, `rows` (each a row document, with its own `input_span`), `rows_read` (the records the reader read, skipped ones included), `rows_skipped` (the records skipped under the server's error allowance), `unsupported_settings`, `unconsumed` and `framing`. Present with a filter attached: `rows_passed` and `rows_cut`, which partition the accepted rows of an `accepted` batch by verdict (`t` against the rest) and read 0 and 0 on any other outcome. Present on a schema with a partition key: `partition_count`, the distinct partitions the stored rows span, which with each row's `partition_id` lets a caller cap the partitions one INSERT touches (`max_partitions_per_insert_block`). Present whenever the outcome is not `accepted` or `accepted_poisoned`: `refused_at` (a `refusal_site` value), `refused_row` for `row`, and `reason` for a decline; `rows_read` is 0 when nothing was read. With an export asked for, exactly one of `row_spans` and `export_declined` is present: `row_spans` when the export ran, one entry per `rows[]` entry, index-aligned, `{off, len}` into `out_export` for an exported row (its whole output line, `\n` included, so slicing the spans out of the bytes is the per-row payload and concatenating them reproduces it) and `null` for a row not exported; `export_declined`, naming the cause, with `export_declined_reason`, the cause's catalog id, when it did not (Conditional members, in the Preamble). When the export ran, `export_columns` is present too: the positional column list of every line in `out_export`, as name objects: the stored non-computed columns in declaration order, independent of the call's `columns` list, a column outside `insertable_columns` included, with the value the library drew, resolved or filled for it, less the columns every row defers (`defer_defaults`). A caller inserts the export naming `export_columns` as the column list; it never derives a list of its own. `export_columns` is the export's only column-list member, so no second list can disagree with it.

The export's truth table, by outcome, export asked for and filter verdict: with no export asked for, `out_export` is NULL and neither `row_spans` nor `export_declined` is present. With an export asked for and the outcome `accepted`, the export runs: `out_export` is the bytes (an empty buffer when no row is exported) and `row_spans` is present, with a span for every row whose outcome is `accepted` and, with a filter attached, whose verdict is `t`, and `null` for every other row (`skipped`, and a `f`, `e` or `d` row under a filter); the rows are exported in body order. With an export asked for and any other outcome (`accepted_poisoned`, `rejected`, `unsupported`), nothing is exported: `out_export` is NULL and `export_declined` names the cause (the outcome, a poisoned value), with `export_declined_reason` `export-batch-not-accepted`. With an export asked for and the outcome `accepted` but the serialization failing, or the export's format unable to carry a stored value, `out_export` is NULL, `export_declined` names the cause and `export_declined_reason` its catalog id; the batch's `outcome` stays `accepted`, with code 0 and no `reason`, so an export decline is keyed by `export_declined_reason`, never by the batch's `reason`. So a caller tells a declined export from an empty one by `export_declined`, never by the buffer, and never slices the payload by an index other than the row's own.

A computed value the export cannot carry. A column the export omits is recomputed by the server that inserts the export. A DEFAULT that reads an EPHEMERAL value is stored, so the export carries its value and the stored row is the same. A MATERIALIZED expression that reads an EPHEMERAL value the row supplied is not: the export carries no EPHEMERAL column, so the inserting server computes the MATERIALIZED value from the EPHEMERAL's type default instead, and the stored row differs from the one the document reports. Such a body's export is declined (`export_declined`, with `export_declined_reason` `export-computed-value-not-carried`): a caller that needs that stored row inserts the body.

Composition. A caller that concatenates accepted bodies into one INSERT (a worker's batch, async inserts) keeps every per-row verdict: a row's `outcome`, its stored values, its `partition_id` and its filter verdict are functions of the row and the schema alone. The whole-body steps are not compositional, and can refuse the concatenation after each body was accepted: the partition split (`max_partitions_per_insert_block`, code 252, bounded by the sum of the bodies' `partition_count`), an insert-time engine merge across bodies, `rowNumberInAllBlocks()` and the like, and a CHECK over a merged async block, which fails every INSERT in it. A caller that must not see those caps its INSERT by `partition_count` and keeps CHECK-bearing bodies isolated. `engine_rows`, present when the table's engine merges rows at insert, is a list of rows, each a list of cells: `{name, stored, null}`, plus `value_b64` for a String or FixedString value. `storage_transforms` entries carry `row`, `column`, `reason` and `stored`, plus `value_b64`; `transformed` entries carry `row`, `column`, `input`, `stored`, `reason` and `lossy`. Every name, rendering, `err` and `export_declined` follows the rule for byte strings in JSON.

`unsupported_settings`, at the top level, is always present: a list of name objects, the call's own settings that the library declined, which every row of the batch shares. It names every setting the call declined, whichever refusal of the call answers; it is empty only when the call declines none, or they could not be read. When it is not empty the batch's outcome is at least `unsupported` (see `batch_outcome`).

`at_merge` lists what an `OPTIMIZE TABLE ... FINAL` of the part this `INSERT` writes would do, at the call's clock instant. It is absent when nothing would happen. `engine_rows` stays exactly what the `INSERT` writer produces, so the two never contradict each other. Each entry is `{part_row, reason, column, stored, input_rows}`:

- `part_row` indexes `engine_rows`: the part's row, not the input body's. Every other `row` member of this document (`transformed[].row`, `storage_transforms[].row`, `refused_row`) and of `filter_result` (`errors[].row`) indexes `rows[]`, the input body's rows, and `input_rows` here does too. An engine's insert-time merge (Collapsing, Replacing, Summing, Aggregating) runs first, inside the `INSERT` writer, so `engine_rows` already excludes the rows it merged away, and after a Summing or Aggregating merge the part's rows do not map one to one to the input's.
- `reason` is a `merge_reason` value: `ttl_delete` (the rows TTL removes the row) or `ttl_column_reset` (a column TTL resets the column's value). A row that is removed and also carries column resets lists only `ttl_delete`: it is removed in the same merge pass, so its column values are never observable.
- `column` names the column, by the rule for byte strings in JSON, and is present only for `ttl_column_reset`.
- `stored` is the column's value after the reset, by the same rule. It is present when that value is decided at the `INSERT`: the column's `DEFAULT` is a constant or a deterministic expression of the row, or the column has no `DEFAULT` (the type's default). It is absent when the `DEFAULT` reads the clock (`now()`) or a generator (`rand()`, `generateUUIDv4()`), and the entry then means that the value is reset at the merge and decided then.
- `input_rows`, when present, lists the input rows, each by its index in the body, that formed the part's row.

The list is "at least these", not "only these": a later background merge can remove more rows as more of them expire. Under `ttl_only_drop_parts = 1`, `ttl_delete` is still reported per row against `OPTIMIZE TABLE ... FINAL`, which drops an expired row from a part that also holds rows that have not expired (measured by the artifact producer). Whether a background merge does the same under that setting is unverified, and the reference stays `OPTIMIZE TABLE ... FINAL`.

Two further fields come from the vendored reader's own state, never from a tokenizer of the library's:

- `unconsumed`: the byte ranges `{off, len}` of the input that the reader's error recovery skipped. It does not account for every record: a **skipped** row's `input_span` can cover more than one input record, when recovery resumed past the end of the record that failed, so the verdicts can be fewer than the body's records while `unconsumed` is empty (measured: one skipped row spanning a three-record body). A record can also be lost while the number of verdicts still equals the number of records, so comparing the verdict count with an independent count of the body's records can be fooled (measured in every format, for example with a multi-line quoted CSV field or a JSON object). In every masked body measured, `unconsumed` was non-empty. Until a batch-level signal from the reader's own framing exists (#478), a caller that needs every record accounted for declines a body that has any skipped row or any `unconsumed` range.
- `framing`: `bom_skipped` (whether the reader skipped a leading byte-order mark), `container` (`array` or `stream` for JSONEachRow, `null` for every other format), and `header` (`{consumed, lines, names}`, `names` as name objects). `bom_skipped` and `header` are `null` where the vendored reader does not expose the decision, and there `null` means not observable, never "no header": the TSV, TSVWithNames and Values readers keep both private (measured by the artifact producer in the source at every supported line). CSV, JSONEachRow and JSONCompactEachRow fill both from the reader's own hooks.

### document:filter_result

A filter evaluation. Always present: `outcome` (a `filter_outcome` value), `code` (Codes, in the Preamble), `err`, `rows_read`, `verdicts` (one `filter_verdict` character per row read, so its length is `rows_read`, and every character `d` under any outcome but `ok`), `unsupported_settings` (a list of name objects) and `errors`, each error or declined row itemized as `{row, code, reason, err}` with `row` indexing the body's rows, `code` nonzero (ClickHouse's for `e`, `CHS_CODE_DECLINED` for `d`) and `reason` the catalog id of a `d`. Present whenever the outcome is not `ok`: `refused_at` (a `refusal_site` value), `refused_row` for `row`, and `reason` for a decline. `err`, at the top level and per row, follows the rule for byte strings in JSON.

`unsupported_settings` (after `rows_read`, before `verdicts`) names the settings the parse itself declined, and then, after them and without repeats, every setting of the filter's own `settings` that this build's filters do not honor in a WHERE. As the batch document's list does, it names every setting the call declined, whichever refusal of the call answers; it is empty only when the call declines none, or they could not be read. When it names one of those, every verdict is `d` and every row is itemized in `errors` as `{row, code, reason, err}` with `code` -2. `outcome` follows its own rules all the same: `ok` for a body a server would accept, and the mirror of `chs_preview_batch`'s verdict otherwise (`filter_outcome`). A declined setting from the `chs_set_defaults`, server or schema layer never reaches an evaluation, because `chs_filter_create` declines first (`schema_description`'s `filter_declined_settings`).

### document:discovery

The column declarations reconstructed from a server's `system.columns` rows, formatted by ClickHouse's own formatter: `{"columns": [...], "columns_sql"}`, where each entry carries `name`, `type`, `default_kind` and `default_expression` as the server spelled them and `declaration`, the formatted declaration, and `columns_sql` joins the declarations for a `CREATE TABLE`. Every one of these is server or DDL text, so each follows the rule for byte strings in JSON.

### input:server_profile

A server's profile, `{"timezone": "<zone>", "settings": {"<name>": "<value>"}, "macros": {"<name>": "<value>"}}`. Every member is optional, so `{}` describes a server with nothing known about it. The profile holds server facts only, in the shape a server's own tables report them, so a caller can fill it from the server it describes; library knobs go in `chs_server_create`'s options instead.

- `timezone`: the server's own zone, the zone its tables bind. An empty string, or no member, means the image zone. The name is validated by ClickHouse's own `DateLUT`, which reads the library host's time zone database.
- `settings`: the settings the server's profile applies to every query, each value a JSON string or the object form for bytes (Input values), never rewritten. A `chtypes_*` knob is never one of them (`chs_set_defaults`). The library accepts exactly what the server's own SET check accepts. `session_timezone` here is the default session zone of the server's user.
- `macros`: the server's macros, as its `system.macros` lists them (`macro`, `substitution`). Absent, they are unknown; present, even as `{}`, they are the complete set where a build applies macros (it advertises `server_profile.macros`; see `chs_server_create`). A build that does not apply them validates the member and declines a macro-reading schema. A macro name that ClickHouse's own macro reader refuses (for example `a.b`) is refused with `CHS_INVALID_ARGUMENT` naming it.

### input:server_options

The options of `chs_server_create` (rule r1). It defines no member yet, so `{}` (or length 0) is the only valid document, and any key is `CHS_INVALID_ARGUMENT`, naming the key. A library knob that is not a server fact lands here, as a new member.

### input:schema_options

The options of `chs_schema_create` (rule r1): how one statement is compiled. Its member is `posture`, a `posture` value, and `{}` (or length 0) compiles in `create`, as before the member existed. A key it does not define is `CHS_INVALID_ARGUMENT`, naming the key, and so is a `posture` that is not one of its values, naming the value.

- `create`: the statement is a `CREATE TABLE` a server would run now, with every check a server's CREATE runs, under the settings layers (`chs_schema_create`).
- `load`: the statement is the stored definition of a table the server already holds, as that server reports it (`system.tables.create_table_query`, `SHOW CREATE TABLE`, or the table's metadata file), compiled as the server loads it when it starts. It is one switch, and ClickHouse's own: every check on the compile's path that reads the loading posture reads `FORCE_ATTACH` instead of `CREATE`, in ClickHouse's own code, and nothing else changes. So the checks a server applies only to a new table are not applied: the type gates (`allow_suspicious_low_cardinality_types`, `allow_suspicious_fixed_string_types` and the rest, at the compile and at every call on the schema), the codec, statistics and suspicious-index checks, the DEFAULT validation of a typed column, the TTL checks, the MergeTree settings' constraint and sanity checks, and the floating-point partition-key, nullable-key and deprecated-syntax gates. `flatten_nested` and `data_type_default_nullable` are not applied either: a stored definition is already flattened and typed. Which checks these are on each supported line is the artifact producer's enumeration from the vendored source; no list is kept here. A projection that a starting server skips because it no longer parses is declined, because whether a given server still holds it depends on that server's history. A Replicated engine's ZooKeeper path and replica name never change a row verdict, so under `load` a stored definition whose engine arguments read a macro the server's `macros` cannot expand (or carry none, as a Replicated database's table does) compiles as the server loads it: `schema_description` then carries no `replicated` member, and only an answer that depends on the path (none today) is declined.

**The caller's obligation.** `load` asserts that the server holds a table defined by exactly this statement. The library cannot check that assertion, because it never connects to the server. A statement a server would refuse at `CREATE` compiles under `load`, and every answer on the schema is the answer for INSERTs into that stored table. If no server holds such a table, every answer describes a table that does not exist, and an accepted row is evidence of nothing. A statement a server reported for a table it holds (its `create_table_query`, `SHOW CREATE TABLE`, or its metadata file) MUST be compiled in `load`, and a statement a caller wrote or edited in `create`. A server's `create_table_query` compiled in `create` can be wrong in both directions, because the server created the table under its own CREATE's settings, which the statement does not carry: an over-reject where a gate was set (a `LowCardinality(UInt8)` column) and an over-accept where a shape setting was (a `Nested` column of a table created with `flatten_nested = 0`).

### input:insert_options

The options of every call that models one INSERT of a body: `chs_preview_row`, `chs_preview_batch`, `chs_block_create` and `chs_filter_eval_body` (rule r1). Its members: `insertable_columns`, `column_defaults` and `verdict_basis`, `defer_defaults`.

- `insertable_columns`: the columns an INSERT may supply, as name objects: the server's column-level INSERT grant (`GRANT INSERT(a, b) ON t`), checked as the server checks it, on the INSERT's header and never on the fields a body supplies. The header is the call's `columns` list, or with none the server's own no-list header: every ordinary and DEFAULT column, in declaration order (so a positional CSV, TSV, Values or JSONCompactEachRow body with no list supplies all of them). A `columns` list may name an EPHEMERAL column, as an INSERT's column list may: its value is read (`value_src` `ephemeral_input`, `is_stored` false) and feeds the DEFAULT and MATERIALIZED expressions that read it, but is not stored; with no list, a body field naming it is an unknown field. The check runs after the list's own refusals (an unknown or ALIAS column, 16; a duplicate, 15; a MATERIALIZED column, 44, unless `insert_allow_materialized_columns` is set, when it needs the grant like any other) and before any byte of the body is read. A header naming a column outside the set is refused 497 (ACCESS_DENIED), with `refused_at` `call`, in every format and whatever the body holds, an empty or a malformed body included. So `columns` MUST be a subset of the set, and a caller whose set does not cover every ordinary and DEFAULT column passes `columns`, at every call that takes this document, `chs_filter_eval_body` included: with a list a call follows the listed INSERT's rules, and with none the no-list rule. A body field naming a column the header omits (a JSON key, a `WithNames` header field) is an unknown field, never a grant question: skipped, or refused 117 under `input_format_skip_unknown_fields` 0 (`refused_at` `row` for a JSON key, `body_read` for a header field), and never stored. An omitted column keeps its declared kind, exactly as with no set: a generator DEFAULT draws (`default_generated`), a clock DEFAULT resolves, a literal DEFAULT fills, a MATERIALIZED column computes and an EPHEMERAL column takes its type default. The export carries every stored non-computed column, those outside the set included (`document:batch`), so the INSERT of the export needs a grant that covers its column list. A Nested column is granted per subcolumn (`n.x`). The set is a grant, not a column list: like a grant it may name an EPHEMERAL or MATERIALIZED column, or a name the table lacks. The 497's message is ClickHouse's own, naming the user `default` and the table `default.t`, since a schema carries neither a user nor a table name; it is informative. Absent is every column. Implemented in the first build that carries this description.
- `column_defaults`: per-call DEFAULT overrides, a list of `{name, value}` (each by the rule for byte strings in JSON). It is one rule: in a cell the server would fill from the column's DEFAULT, the call uses the caller's `value` instead. A supplied value wins: the override fills exactly the cells ClickHouse's own input format marks missing for that column under the call's format settings, as the vendored reader decides it, and no other: a field the record omits, a `null` for a non-Nullable column under `input_format_null_as_default` 1, and an empty CSV field under `input_format_csv_empty_as_default` 1. An empty JSON string `""` is a supplied value. A Nullable column's `null` stays `NULL` where the server keeps it (the implementing build confirms this against the server's own missing mark). Such a cell reads `default_override`, and everything that reads the column sees the value as an INSERT that supplied it would: a CHECK, the sorting, primary and partition keys, a skip index, a projection, a TTL, a MATERIALIZED or DEFAULT expression that reads it, and a filter. The export carries it as a stored, present value at the column's position in `export_columns`, so the INSERT of the export needs no override, and a column the override fills is not deferred in those rows (`defer_defaults`). An entry may name an ordinary or a DEFAULT column, and an EPHEMERAL column where the implementing build measures it equal to a supplied EPHEMERAL value; an entry that names an unknown column, a column that is not insertable, or a MATERIALIZED or ALIAS column is `CHS_INVALID_ARGUMENT` at `call`, naming `column_defaults[i]`. When `insertable_columns` is given, an entry's column MUST be in it, because the INSERT the override models names the column in its header; one outside it is the same `CHS_INVALID_ARGUMENT`. `value` is read in the body format's own field encoding, as if the record supplied this field; a value that does not read as the column's type is `CHS_INVALID_ARGUMENT` at `call`, naming `column_defaults[i]`, before any byte of the body is read. Implemented: the build advertises it as `insert_options.column_defaults` in `chs_build_info`'s `capabilities.features` (rule r9).
- `verdict_basis`: `input`, the default, or `export`: what row a filter verdict answers for. Under `input`, a filter that reads a value the library drew or resolved itself is `d` (`drawn-value`), because the server would draw its own. Under `export`, the verdict answers for the row the export would store, so a drawn or resolved value is answerable, and the caller MUST insert the export. Reserved: declined at `export` until implemented.
- A member whose value is a list or an object is refused `CHS_INVALID_ARGUMENT` when an entry does not match its shape, naming the key. `{}` (or length 0) is the INSERT these calls modeled before the document existed, byte for byte. Each member means the same at every call that takes the document. A key it does not define is `CHS_INVALID_ARGUMENT`, naming the key, and so is a value that is not one of the member's, naming the value; a member this build does not implement declines as Input documents (in the Preamble) says.

- `defer_defaults`: `none`, the default, or `server` (public issue #479). `server` defers to the server each DEFAULT this build would otherwise decline because its value is the server's to compute (a generator or a server function the build does not admit). Such a column reads `default_deferred` in the rows that omit it, and the export omits it from those rows' lines. What reads it there is not answered (the deferred-column rule): a filter that reads it makes the row's verdict `d` (`verdict_code` `CHS_CODE_DECLINED`, `verdict_reason` `defer-defaults-reader`); a CHECK, a sorting, primary or partition key, a skip index, a projection, a TTL, or a MATERIALIZED or other DEFAULT expression that reads it declines the row (`unsupported`, `reason` `defer-defaults-reader`); and such a row carries no `partition_id`. Admitted generators keep drawing (`default_generated`), so a drawn id stays usable for deduplication. A body is mixed when its exported rows' lines would not all omit the same columns (some rows supply a deferred column and others omit it). The export has one column list, so a mixed body is declined, and only when an export is asked for: the batch is `unsupported`, `refused_at` `body_step`, `reason` `defer-defaults-mixed-body`; with no export asked for no line omits anything, and the batch is answered. A body whose rows all defer the same columns, or none, is never mixed: its export omits those columns from every line and from `export_columns`. Implemented: the build advertises it as `insert_options.defer_defaults` in `chs_build_info`'s `capabilities.features` (rule r9).

### input:filter_options

The options of `chs_filter_create` (rule r1): how one filter is compiled. `{}` (or length 0) compiles as before the document existed. ### chs_abi_revision

The v0 tombstone. It always returns `CHS_ABI_REVISION_TOMBSTONE` (1001). It must never be removed, and its name must never be given another meaning.

A sweep of every released binding (every minor from 0.1 to 0.5, in all four languages; [the CI run](https://github.com/Wave-RF/chtypes/actions/runs/36939764841)) measured why: each one calls this symbol whenever it exists and refuses cleanly, naming both numbers, when it returns a revision other than its own, but treats a MISSING symbol as "revision 0, predates the probe" and goes on to call `chs_init`. So this tombstone is what turns every v0 binding away before it can reach any other symbol, and `gen.py --check` refuses a description that reuses a v0 name without it. A binding of generation 1 or later never calls it; the loader resolves it only to prove it is present.

### chs_initialize

Sets this image's server zone, once per process: the zone every compiled type binds, and the zone a call without its own `session_timezone` runs in. `timezone` is counted bytes, and length 0 means `UTC`. The name is validated by ClickHouse's own `DateLUT`, so a name it cannot load is `CHS_REJECTED` with `DateLUT`'s own code and message. A second call with the same spelling is a no-op that answers `CHS_OK`; a different spelling is `CHS_INVALID_ARGUMENT`, naming both. The spelling is compared byte for byte and never canonicalized, because it is observable: `timezoneOf` over a column reports the image zone exactly as spelled.

The zone is process state, not a per-call parameter, because ClickHouse's own MergeTree code reads the server zone directly (`DateLUT::serverTimezoneInstance`). A per-call zone is the `session_timezone` setting instead. A loader calls this once, after the handshake checks and before any other call; the list of type families the build must refuse is embedded when the library is built, so nothing else is passed in.

### chs_set_defaults

Seeds the settings every later call starts from, as a JSON object whose values are JSON strings, or the object form for bytes (Input values), and a binding never rewrites a value, a boolean included. Each successful call replaces the previous defaults whole. A setting name the server would refuse is refused here, with ClickHouse's own code and message, and nothing is committed. `session_timezone` here is the default zone for later calls; it does not change the image zone that compiled types bind.

The library's own knobs are `chtypes_*` settings, and this is the only channel for the process-level ones. Each is an integer or a string given as a JSON string, and no server knows one, so a server profile refuses it (115) and a call's settings carry only the per-call ones. The knobs, their layer, type, default and effect: `chtypes_now_epoch_nanos` (per call, int64 nanoseconds since the epoch, default the wall clock: pins the call's clock instant); `chtypes_clock_offset_nanos` (per call, int64, default 0: shifts the instant); `chtypes_max_clock_skew_nanos` (per call, int64, default 0: the skew budget a clock-reading expression may resolve under); `chtypes_default_eval_memory_bytes` (process, int64 bytes, default 268435456, 0 disables: the admission memory budget one DEFAULT, CHECK, TTL or filter evaluation may use); `chtypes_default_eval_cpu_nanos` (process, int64, default 1000000000, 0 disables: the admission time budget, the evaluating thread's CPU time, detected not interrupted; the earlier name `chtypes_default_eval_wall_nanos` is refused on v2 with `CHS_INVALID_ARGUMENT` naming this one); `chtypes_custom_settings_prefixes` (process, string, default this version's shipped server config value, `SQL_` on every supported line, and no prefix for a version whose shipped config names none: the server's `custom_settings_prefixes`, comma-separated). The three clock knobs are per call only: `chs_set_defaults` and a schema's settings refuse them with 115, as a server profile does. A process knob in a call's settings is declined, named in `unsupported_settings` (`call-setting-process-only-key`), and a clock knob whose value is not an integer likewise (`call-setting-clock-value`). An evaluation that exceeds a budget is declined with that budget's own reason id, never answered: `admission-memory-budget` for the memory budget and `admission-time-budget` for the time budget; the earlier single id `admission-envelope` is retired, its catalog entry naming both successors (rule r4). The time budget is the evaluating thread's CPU time, not wall time. Each catalog entry states its load dependence. A memory-budget decline is deterministic (`measured`). A time-budget decline depends on load only near the budget: CPU time rose up to x1.03 under load on linux-arm64 and up to x2.0 on linux-amd64 when two busy hardware threads share a core, so a time-budget decline is retry-stable when the evaluation costs more than the budget on an idle core and never happens under about half of it; between half and one times the budget the host's load can decide. Normal evaluations cost about 1000 times less than the 1 s default. a schema whose DEFAULT exceeds a budget at admission is declined at compile. The defaults are this description's, not a build's: a build reports nothing about them.

Setup only. The defaults are immutable once this image has created its first `chs_schema` (a filter or a block needs one): from then on the call changes nothing and answers `CHS_INVALID_ARGUMENT`. No call ever reads defaults that change under it, so no binding needs a lock around them.

Unloading the library, or initializing it again in the same process, is unsupported: a loader never unloads a library.

### chs_server_create

Describes one ClickHouse server, from a profile document (`input:server_profile`): its `timezone`, judged by ClickHouse's own `DateLUT`; its `settings`, judged by the server's own SET check; and its `macros`, read by ClickHouse's own `Macros` configuration reader, as a server reads `<macros>`. Every member is optional, and a member the profile omits is not described: the image zone applies, there is no server settings layer, and the server's macros are unknown. `options` (`input:server_options`) defines no member yet.

Everything is validated here, once, and the server never changes after it. A key the profile or the options document does not define is `CHS_INVALID_ARGUMENT`, naming the key, and so is a document that is not a JSON object, a member of the wrong JSON type, a NUL in the zone, an empty macro name, a NUL in a macro's name or value, or a macro set that ClickHouse's own reader does not read back exactly as given (a `.` in a name is one). A zone `DateLUT` cannot load is `CHS_REJECTED` with `DateLUT`'s own code and message (36, BAD_ARGUMENTS). A setting the server's SET check refuses is `CHS_REJECTED` with the server's own code and message: 115 (UNKNOWN_SETTING) for a name the server does not know, a library knob such as a `chtypes_*` setting included, because a server's profile holds ClickHouse settings only. Nothing is created on any refusal.

`CHS_DECLINED` is reserved: a build that will not describe a profile declines it, which is never a wrong answer. The one decline foreseen is a setting outside the set that shapes an input, at a value other than its default, once that set is generated from the vendored source.

This build validates a profile's `macros` but does not apply them: a schema whose engine arguments or expressions read a macro is `CHS_DECLINED` (reason `server-macros-required`, or `server-dependent-function` for `getMacro`) whether `macros` is absent, `{}` or names the macro, as it is without a server, except under `schema_options`' `posture` `load`, where a stored Replicated definition compiles without expanding them (`input:schema_options`). Applying them is reserved behavior (rule r9): a build that applies them advertises `server_profile.macros` in `chs_build_info`'s `capabilities.features`, and this build does not. For a build that advertises it, `macros`, when present, even as `{}`, is the server's whole `system.macros` (`input:server_profile`), so a macro a Replicated engine's arguments name that the set lacks is then the server's own refusal (`CHS_REJECTED`, 139, NO_ELEMENTS_IN_CONFIG). A build that does not advertise it declines as described above.

A setting this build's filters do not honor in a WHERE is no decline here, and the call succeeds. So does `chs_schema_create` on the server: it lists the setting in the schema's `filter_declined_settings` (`schema_description`), at layer `server`.

The call reads no defaults and leaves `chs_set_defaults`' latch open. Its init class is `required`, so before `chs_initialize` it refuses (Initialization, in the Preamble).

### chs_server_free

Releases the caller's reference to a server. Schemas created on it keep it alive. Freeing NULL does nothing.

### chs_schema_create

Compiles exactly one `CREATE TABLE` statement (columns, engine, keys, TTL, settings and constraints) with ClickHouse's own parser and the checks a server's CREATE runs, on `server`, under a profile of settings given as a JSON object of string values. A trailing semicolon is allowed. A second statement is refused the way ClickHouse's own parser refuses one in a single query (`CHS_REJECTED`, with its code and message), and a statement of any other kind is `CHS_INVALID_ARGUMENT`, except under `posture` `load`: there a `CREATE VIEW`, `CREATE MATERIALIZED VIEW` or `CREATE DICTIONARY` statement, the stored definition of an object a server lists in `system.tables` and whose columns it lists in `system.columns`, is `CHS_DECLINED` with the reason `engine-not-modeled`, so a caller that compiles a server's stored definitions falls back for it as it does for an engine this build does not model. The `ATTACH` spellings of those kinds that a server refuses with 62 stay `CHS_REJECTED` with that code, as the server answers. An `ATTACH TABLE` statement is not one of the other kinds (`options`, below). The library models a table, not its database's engine: `ATTACH TABLE` with a column list and an engine but no UUID is accepted under `posture` `load`, which a server's Atomic database refuses (80), and under `create` it is declined (`attach-statement-under-create`).

A table whose engine this build does not model (a `Distributed` or `Buffer` table, for example) is `CHS_DECLINED` with the reason `engine-not-modeled`, which is returned only when the engine itself is the cause: a decline for anything else in the statement carries that thing's own reason.

`server` is the server the table is on (`chs_server_create`), or NULL. On a server, the schema's home zone is the server's `timezone`: its zone-less `DateTime` and `DateTime64` columns bind it, as a restarted server binds its own, and every call on the schema that names no `session_timezone` runs in it. The server's `settings` layer under the schema's own, and a Replicated engine's ZooKeeper path and replica name read the server's `macros` (which a build applies only when it advertises `server_profile.macros`; this one does not: `chs_server_create`). With `server` NULL the schema is on the image's own server, exactly as before servers existed: the image zone, no server settings layer, and macros unknown. A freed server, a handle of another kind or a server from another library image is `CHS_INVALID_ARGUMENT`. The schema holds a counted reference to its server, so the caller may free the server at any time.

`timezone()` (and its alias `timeZone()`) in a DEFAULT, MATERIALIZED or CHECK expression is admitted on a schema created on a server whose profile names a `timezone`. On a server schema, `timezone()` answers the server's zone when no session zone is in force; a session zone that would change the answer is declined (named in `unsupported_settings`). That applies equally to a profile whose `settings` carry `session_timezone`. On a schema with no server, or a server whose profile names no `timezone`, it stays refused as a server constant. `serverTimezone()` is refused on every schema.

A setting this build's filters do not honor in a WHERE, from the `chs_set_defaults` snapshot this call captures, the server profile or this call's own `settings`, is no decline here: the call succeeds and lists it in the schema's `filter_declined_settings` (`schema_description`), and `chs_filter_create` on the schema declines.

`options` (`input:schema_options`) sets the `posture` the statement compiles in: `create`, the default, or `load` for a server's own stored definition (see `input:schema_options`, and the caller's obligation there). A `posture` this build does not know, or any other key, is `CHS_INVALID_ARGUMENT`, naming it. An `ATTACH TABLE` statement is a stored definition, never a statement of another kind: under `create` it is `CHS_DECLINED`, ch_code 0, with exactly the message `chs_schema_create: an ATTACH TABLE statement is a stored definition; compile it with schema_options {"posture":"load"}; declined rather than answered`, and under `load` it compiles as the same definition spelled `CREATE TABLE`.

A schema whose compile needs its server's zone is declined on a host thread that already runs a ClickHouse query of its own: `CHS_DECLINED`, which is never a wrong answer.

The result is immutable: nothing changes a schema after this call, so it replaces v0's column-list compile and its engine, TTL and partition-key setters, and any number of threads may use it at once. Its types bind its home zone (Zones, in the Preamble: its server's `session_timezone` when set, else its server's `timezone`, else the image zone), never the `session_timezone` in its own settings, which is the zone of this call and of the later calls on the schema that name none of their own.

### chs_schema_free

Releases the caller's reference to a schema. Filters and blocks made from it keep it alive. Freeing NULL does nothing.

### chs_schema_describe

A JSON document describing the schema's columns, owned by the caller; it replaces v0's borrowed column accessors.

A schema compiled in `load` carries `"posture": "load"`; one compiled in `create` carries no `posture`.

A schema `chs_schema_create` returned always describes: the walk this document needs runs at compile, so a deep statement is refused there (`CHS_REJECTED`, 306) and this call never refuses or declines a compiled schema. It is never `CHS_INTERNAL`.

### chs_preview_row

Validates and coerces one row of `body` under the schema, as a server's INSERT would, and returns the row's document. `columns` is the INSERT column list, a JSON array of name objects (`{name}` or `{name_b64}`), and empty for none. `session_timezone` in `settings` is this call's zone.

`body` holds exactly one row, and the library reads all of it, with the same reader as `chs_preview_batch`. A malformed tail, or trailing content the format's reader does not itself skip, is rejected with the reader's own code, as a server's INSERT rejects it; what the reader skips, such as a trailing newline, is fine. A body holding no row, or more than one, is `CHS_INVALID_ARGUMENT`, naming the call: `chs_preview_batch` answers a body of many rows. The row's document equals the single row of `chs_preview_batch`'s document for the same body, and stands for the call: a refusal or decline of the call, its settings, its column list or its options is this document's `outcome` with `refused_at` `call`, never a status.

`options` (`input:insert_options`) shapes the INSERT the call models, and `{}` is the INSERT it modeled before the document existed.

### chs_preview_batch

Validates and coerces a whole body, which may hold many rows, and returns the batch document, with the same declines as `chs_preview_row`. Row separation and the server's error allowance are ClickHouse's own, and the document's `unconsumed` and `framing` say what the reader skipped and how it framed the body. `filter`, when given, is evaluated over each stored row in the same parse. When that filter's WHERE would read a setting this build's filters do not honor, from the filter's own `settings`, the name joins the batch document's top-level `unsupported_settings` and the batch is `unsupported` by `batch_outcome`'s step 2: every row `unsupported`, filter rows `d`, and no export. The same call without the filter is unchanged. `export_format` is `CHS_EXPORT_NONE` or a `chs_format` the build can write; with an export that runs, `out_export` receives the accepted rows serialized once, an empty buffer when the batch holds no row. ### chs_filter_create

Compiles a boolean SQL expression over the schema's columns, binding its query parameters (a JSON object of string values) by ClickHouse's own substitution, so a value is never SQL text. A parameter's value is decoded by ClickHouse's escaped-text reader, exactly as a server decodes an HTTP `param_` value (`input:filter_options`' `param_encoding`, `escaped`): `\b` is an escape, so the parameter `a\b` reads as two bytes, `a` and 0x08, and a literal backslash is written `\\`; `\N` reads as the empty value; `\x41`, `\'` and `\0` decode as that reader decodes them; a raw tab or newline is `CHS_REJECTED` with 457 and a trailing backslash with 25, as a server refuses them; and the bytes an escape produces are kept, valid UTF-8 or not. The object form `{"b64": ...}` (Input values) is decoded from base64 first, and its bytes are then read the same way. `options` (`input:filter_options`) shapes the compile, and `{}` is the compile before the document existed. `settings` is the profile the expression is compiled under, so `session_timezone` there is the zone of its literals. Non-deterministic expressions are declined.

The WHERE's settings are layered, lowest first: the build's own, `chs_set_defaults`, the schema's server profile, the schema's own settings, and then this call's `settings`; `session_timezone` at every layer stays on the zone path. A type gate in the schema's own settings binds the CREATE only, so a WHERE's CAST validates under the session layers, every layer but the schema's own.

On a schema whose `filter_declined_settings` is not empty (`chs_schema_describe`), from any layer, the call is `CHS_DECLINED` with ch_code 0. It is checked after the argument checks and before the expression is parsed, because `dialect` can change the parse, and the message names each setting and its layer, in the list's order: `chs_filter_create: the settings this schema was compiled under set <a> (<layer>), <b> (<layer>), which this build's filters do not honor in a WHERE (listed in chs_schema_describe's filter_declined_settings); declined rather than answered`, where each `<layer>` is the entry's `declined_layer` value, with the reason `server-profile-setting`. The message is informative; the entries are joined by a comma and a space, in the list's order, and each name renders verbatim. A `name_b64` entry renders as `b64:<base64>`; it does not occur in practice, because a setting name ClickHouse does not know is refused earlier, with 115. The server and the schema were created all the same: no settings layer changes a schema compile.

**Changed (public issue #588).** A declined setting from the `chs_set_defaults` or the schema layer moves from evaluation time to create time: it was named at evaluation (`filter_result`'s `unsupported_settings`), and it now declines this call. A server-profile setting already declined it.

A key of this call's own `settings` other than `session_timezone` is never `CHS_DECLINED` here but for one case, and it is never in `schema_description`. The case is a cell of the line's `where-settings/documented-pathological.tsv`, a value under which the server refuses every query: set in this call's own `settings`, it is `CHS_DECLINED` with ch_code 0 and the reason `setting-server-refuses`, because no verdict under it could stand. A key in this build's honor set is applied to the WHERE; a key passed through is accepted and ignored; and a key this build's filters do not honor is reported at evaluation (`filter_result`'s `unsupported_settings`, every verdict `d`, and `chs_preview_batch`'s). The WHERE runs under this call's layers only (the defaults, the server profile, the schema's own settings and this call's), as a subscriber's SELECT in its own session would. An evaluation's `settings` (`chs_filter_eval_body`, `chs_preview_batch` with a filter, `chs_block_create`) are the INSERT session's: they govern parsing the body and the expressions the INSERT itself evaluates (Settings, above), and never reach the WHERE, so they are never named as WHERE settings. So a filter evaluated in the INSERT's own session, a materialized view's WHERE for example, is created with that session's WHERE-tier settings in its own `settings`. Every key still meets the server's own SET check first, so a name the server does not know is `CHS_REJECTED` with ch_code 115.

A filter under a per-call `session_timezone` answers as the artifact producer has measured against live servers, including how the zone in an evaluation's settings combines with the zone the filter was compiled under. Until a path is measured to match a server it declines, which is never a wrong answer. The filter holds a counted reference to the schema.

### chs_filter_free

Releases the caller's reference to a filter. Freeing NULL does nothing.

### chs_filter_eval_body

Evaluates the filter over every row of a body, returning one verdict per row. `settings` is the INSERT session's: it governs parsing the body and the expressions the INSERT evaluates (Settings, above), and `session_timezone` there is this call's zone. `columns` is the INSERT column list, a JSON array of name objects (`{name}` or `{name_b64}`), and empty for none, read exactly as `chs_preview_batch` reads it: with a list the call models the INSERT that names it, and with none the INSERT that names none. When a server would not accept an INSERT of the body, because `chs_preview_batch`'s verdict over the same body, settings and column list, with no filter, is not `accepted`, every verdict is `d` and the outcome mirrors that verdict (`filter_outcome`). The call reads an accepted body once, for its verdicts and that batch verdict together, and under any outcome but `ok` writes `d` for every verdict, answering a refusal or decline of the call itself in the document (`refused_at` `call`), never as a status. `options` (`input:insert_options`) is that INSERT's, read as `chs_preview_batch` reads it, so the verdict mirrored is `chs_preview_batch`'s over the same body, settings, columns and options.

### chs_block_create

Parses a body once under the schema, for evaluating many filters over it. `settings` is the INSERT session's: it governs the parse and the expressions the INSERT evaluates (Settings, above), `session_timezone` there included, and `columns` is read as `chs_preview_row` reads it. The block holds a counted reference to the schema. It also records `chs_preview_batch`'s verdict over the same body, settings, columns and options, with no filter, which `chs_filter_eval_block` answers by; a refusal or decline of the call or the body is recorded there, so this call returns a status other than `CHS_OK` only for misuse or an internal error. An accepted body is read once, for the block and that verdict together. `options` (`input:insert_options`) is read as `chs_preview_batch` reads it.

### chs_block_free

Releases the caller's reference to a block. Freeing NULL does nothing.

### chs_filter_eval_block

Evaluates the filter over a parsed block. Over a body a server would accept, it gives the same answers `chs_filter_eval_body` gives for that body. Over one it would not (the verdict `chs_block_create` recorded is not `accepted`), the outcome mirrors that verdict as for `chs_filter_eval_body`, and every verdict is written `d`, the rows before the refused one included: the two calls write the same document for the same body, and the rule that any non-`ok` outcome means every verdict is `d` holds in the data. `refused_at` and `refused_row` say where the refusal sat (`row` for a refused row, `body_step` for a whole-body step or a poisoned value, `call` for the block's own settings). It takes no settings: the filter brings the settings it was compiled under and the block those it was parsed under. The filter and the block must come from the same schema; a pair from two schemas is `CHS_INVALID_ARGUMENT`.

### chs_discover_query

The query a caller runs against a server to read a table's `system.columns` rows, so that no binding holds SQL of its own. It is the connect-time way to rebuild a table's columns from a server. A server's `SHOW CREATE TABLE` output also compiles under `chs_schema_create`: from live 26.3, 26.7, 26.8 and 26.9 servers, all 32 shapes measured (8 per line, `ENGINE = Memory` included) compile under `posture` `create` and `load` (`measured`; compiling is `CHS_OK`, and the compiled columns were not compared with the server's). It takes no input. The SQL names the table through the query parameters in `discover_query_param` (`{database:String}` and `{table:String}`), which the caller binds when it runs the query; it selects exactly the `system.columns` fields `chs_discover_columns` reads, `FORMAT JSONEachRow`.

### chs_discover_columns

Reads a server's `system.columns` rows (the JSONEachRow answer to `chs_discover_query`'s query) with ClickHouse's own reader and returns the column declarations, formatted by ClickHouse's own formatter.
