# Fetching, verifying and installing v1 artifacts — the OCI contract every SDK implements

> **Status: in progress, on the `v1` branch only.** `main` still ships 0.5.x against [`fetch.md`](fetch.md); nothing here is live until the switch (the v1 fetch-layer plan's §2.4). This page is the normative contract for the v1 fetch layer: an OCI registry, zstd-compressed layers, and a key-based Sigstore bundle per platform manifest, replacing today's release directory and `SHA256SUMS`. Where this page and the delivery side's `layout-v2` design disagree, that design's own §0 wins, and this page is a bug until it is corrected.

Four thin per-language fetchers share one wire contract: resolve a floating or exact version against an OCI registry, verify a signed statement that binds the platform, the version and the ABI generation to the bytes, then unpack and cache the result. No SDK speaks both v0 and v1; the switch (§2.4 of the plan) is a clean cut, not a fallback. `scripts/fetch.sh` retires at v1 and is not replaced — every binding fetches for itself.

The source of truth for every value this page cites is [`spec/fetch-v1/constants.json`](../../spec/fetch-v1/constants.json), generated by [`scripts/fetch-v1/gen-constants.py`](../../scripts/fetch-v1/gen-constants.py) into all four bindings and into the reference table below. Nothing in this page repeats a value the generator does not also produce — a number quoted twice is a number that can drift, so §7 and §8 are generated, never hand-typed.

## 1. The cache

A standard **OCI image layout** rooted at `${XDG_CACHE_HOME:-~/.cache}/chtypes/v1/` (`CHTYPES_CACHE` names the layout directory itself, overriding the whole path, not a parent of it). This is a v1-only root: it shares nothing with v0's `…/chtypes/artifacts/abi<R>/` caches or with a developer's local build caches under `…/chtypes/` — a fetch here never reads or writes either.

- `oci-layout`, `index.json` and `blobs/sha256/<hex>` are the OCI image layout proper: every manifest, index and layer blob this fetcher has verified, content-addressed.
- `unpacked/sha256/<manifest-hex>/` sits beside `blobs/`: the unpacked library for one verified platform manifest, named by that manifest's own digest. A `verified.json` record inside it is the fetch layer's own durable proof that this directory was verified once, under which key, and against which digests — **the source of truth for `--offline` and `resolve_installed`** (never `index.json`; see below).
- `index.json` is written by **temp-file-then-atomic-rename**, then re-read and re-applied, never edited in place — two concurrent fetches racing the same cache must both survive (the `index-race-reapply` case, §10).
- Read-only **system directories** are searched after the user cache, never written to.
- The cache **can be pre-seeded** with `oras copy -r --to-oci-layout` (ORAS 1.3.4 and `--platform` are `measured` compatible with this layout, per the delivery side's design). A pre-seeded layout has entries in `index.json` with no corresponding `unpacked/` directory yet; the first request for one verifies it against its signature exactly as a freshly downloaded layer would, then unpacks it. Losing a pre-seed's `index.json` entry to a losing race costs only `oras` interop, never correctness — verification never trusts `index.json` content, only digests it then independently checks.

## 2. Sources

- **Base URLs** are an ordered, repository-qualified list (`https://registry.wavehouse.dev/chtypes/v1` by default; `CHTYPES_ARTIFACTS_URL`, comma-separated, replaces it). A mirror's repository path may differ (for example a GHCR mirror), which is why a base names the whole repository root, not just a hostname.
- Bases are tried **in order on a temporary error** (a timeout, a 5xx, a connection refusal) and **never on a verification failure** — a base that serves a byte-for-byte wrong artifact is a fault to report, not a reason to go shopping for a base that will lie more conveniently.
- **No hostname pinning.** Trust comes entirely from the signature (§4); any base, including a third-party mirror, is equally trusted once its bytes verify.
- `HTTPS_PROXY`/`NO_PROXY` and the system certificate store are honored by every binding's own HTTP stack (`net/http`, `urllib.request`, Node's `https`/`http` with `tls.getCACertificates`, `ureq`'s platform verifier) — never a bespoke TLS or proxy implementation.
- `CHTYPES_DOWNLOAD_TOKEN`, when set, is sent as `Authorization: Bearer <token>` to the configured base hosts only (exact host match), **never forwarded across a redirect**, and never required by the default host.
- **Redirects** are followed up to `limits.max_redirects` hops, with `Authorization` dropped on any cross-origin hop. The default host never redirects a blob GET (it serves bytes directly); a mirror may, so the handling stays in every binding regardless.
- `CHTYPES_REGISTRY` (the v0 variable) is **retired**: set, it produces exactly one loud warning and is otherwise ignored. `CHTYPES_ARTIFACTS_URL` is v1's equivalent.

## 3. Resolve

`GET /v2/<repository>/manifests/<tag>` for the requested spelling (a two-, three- or four-part version) returns a multi-platform **OCI image index**. The fetch layer:

1. selects the descriptor for the running platform (`os`/`architecture`); no match is `CHTYPES_ARTIFACT_UNPUBLISHED`, naming what the index actually offers;
2. `GET`s that platform's manifest **by digest**, and verifies the fetched bytes' sha256 and size against the index descriptor before parsing anything inside it;
3. reads the manifest's own layer descriptor (exactly one layer: the library tarball) and config descriptor, without yet trusting either — trust is established in §4, never assumed from shape.

An index, manifest or layer whose media type the fetch layer does not recognize is `CHTYPES_SOURCE_INCOMPATIBLE` — a protocol-shape problem, never a trust problem. The version spelling itself is checked against `spelling.regex` **before any network call**; a `v`-prefixed or channel-suffixed spelling (`v26.8`, `26.8.15.10-lts`) is refused immediately with a hint naming the v1 spelling (`spelling.refuse_hint_regex`).

## 4. Trust

Each platform manifest's signature is one or more **Sigstore bundle v0.3** referrers (`application/vnd.dev.sigstore.bundle.v0.3+json`), found through the OCI **referrers API** (`GET /v2/<repository>/referrers/<manifest digest>`, filtered by `artifactType`) or, when a host does not serve that API (a mirror may not), the **fallback tag** `sha256-<hex>`. Both are implemented in every binding — never only one, because which a given host serves is a property of that host, not of this fetcher.

**A manifest can carry several referrers of the signature artifactType at once** — a key rotation adds a **second** bundle rather than a second signature inside one envelope (§0 of the delivery side's design) — and a manifest also carries a separate goldens referrer (one per platform manifest, D7) with its own artifactType. The fetch layer therefore:

- always filters referrers by `artifactType` itself, never assuming a referrers listing holds only one kind of object;
- accepts the manifest's signature as soon as **any** referrer of the signature artifactType verifies under a trusted key — it does not require every bundle present to verify, and it does not stop at the first bundle that fails to.

Verifying one bundle:

1. parse the bundle JSON;
2. compute the DSSE envelope's **pre-authentication encoding (PAE)** over the payload;
3. verify one ed25519 signature against the trusted key list, using the primitive each binding already ships for v0 (Go `crypto/ed25519`, Python's own RFC 8032 verifier, Node `node:crypto`, Rust `ed25519-dalek`) — never a new Sigstore client library, and never a bundle whose model requires a certificate (sigstore-python and sigstore-rs cannot verify a key-only bundle at all; this is why every binding hand-verifies instead of delegating to one);
4. parse the in-toto **Statement v1** payload and check it against the request:
   - `predicateType` must equal `predicate_types.artifact` (the reference table below);
   - `subject[].digest.sha256` must equal the manifest's own layer digest;
   - the predicate's `abi` must equal `abi_generation` (**never** `abi_revision` — that key name is v0's, and a v1 statement must not be readable as v0 revision 1);
   - the predicate's `os` and `arch` must equal the requested platform;
   - the predicate's `clickhouse_version` must **equal** an exact four-part request, or **lie within** a floating one (a component prefix: `26.8.15.10` is within both `26.8` and `26.8.15`).
   - A duplicate key anywhere in the statement's JSON is `CHTYPES_ARTIFACT_CORRUPT` — every binding's JSON parse refuses one rather than silently taking the last value.

Any of the above failing is `CHTYPES_ARTIFACT_CORRUPT`; no referrer of the signature artifactType verifying under a trusted key at all is `CHTYPES_ARTIFACT_UNTRUSTED`. `CHTYPES_ALLOW_UNSIGNED=1` skips verification with one loud warning, exactly as in v0 — never silently.

The default trust list is the release key below (§0/§4.2 of the delivery side's design: **no rotation for v1**, the same key v0 ships). `CHTYPES_TRUSTED_KEYS` **replaces** the default list, never appends to it. A second, fixture-only test key exists for this repository's own conformance suite (`tests/fixtures/fetch-v1/test-key/`); it is in the generated constants as `TEST_KEYS`, `trusted_by_default: false` always, and is never part of any production build's trust list — a case opts into it explicitly (`request.trust: "test"` in `cases.json`).

**After `dlopen`**, the FFI layer additionally checks the predicate against the loaded library's own build info (`chs_build_info()`) — `abi_fingerprint`, `library_sha256` and `glibc_floor` are carried through by the fetch layer **opaque**: it never interprets them, never checks glibc, and never dlopens. A mismatch there is `CHTYPES_ARTIFACT_INCOMPATIBLE` (§8), raised by the loader, not by this layer; see the FFI lane (not yet built — blocked on the ABI v1 design) and §9 below.

## 5. Bytes and unpack

`GET /v2/<repository>/blobs/<layer digest>`, downloaded to a temp file **while hashing**:

1. check the downloaded size and sha256 against the manifest's layer descriptor **before any decompression** — a `tampered-layer` case must show no unpack attempted and the temp file removed, never a partial decode of untrusted bytes;
2. zstd-decode (multi-frame streams are accepted; a window log above `limits.zstd_window_log_max` is refused as `CHTYPES_ARTIFACT_CORRUPT` before the decoder allocates for it);
3. unpack the tar stream with per-entry checks: **regular files and directories only** — a symlink, hardlink, device file, absolute path or `..` path segment is `CHTYPES_ARTIFACT_CORRUPT`, and so is a duplicate entry name;
4. enforce `limits.max_unpacked_bytes` as the tar stream is written, not after;
5. **re-hash the installed library** against the signed predicate's `library_sha256` and compare its size to `library_bytes` — the same load-time re-verification v0 performs, now against the OCI-delivered bytes.

Every one of the checks above runs **in this order**, and a failure at any step removes whatever partial state it produced — no half-unpacked directory is ever left where a later `--offline` read could find and trust it.

## 6. Lock schema 3 and `--frozen`/`--offline`/`update`

`chtypes.lock`, schema 3 (`spec/fetch-v1/schema/lock3.schema.json`), replaces v0's schema 1 and 2 outright — **a v0 lock is refused** (`CHTYPES_ARTIFACT_PINNED`, naming re-lock), never silently reinterpreted. Per declared platform, it records the request, the exact resolved version and build, and the **platform manifest, layer and bundle digests** — never a hostname, so a lock is mirror-portable. The **index digest is informational only**: under option (a) of the delivery side's design the index is computed by the Worker, not stored, so a by-digest GET of it is not guaranteed to be served, and `--frozen` never fetches it.

- `fetch --lock` resolves normally (§3–§4) and then writes the lock.
- `--frozen` **skips resolution entirely**: it fetches the platform manifest, bundle and layer by digest from any configured base, verifies them exactly as a normal fetch would (§4–§5), and refuses (`CHTYPES_ARTIFACT_PINNED`) if the lock names no entry for the requested platform, or the lock itself fails schema validation. A tree with **no tags, no referrers API and no `tags/list`** still succeeds under `--frozen` — every request it makes is by digest (the `frozen-no-discovery` case).
- `update` re-resolves every locked request against the current index and rewrites the lock; it never merges a stale entry with a fresh one.
- `--offline` reads the cache only (§1): the **source of truth is the immutable `unpacked/sha256/*/verified.json` records**, never `index.json`. A pre-seeded `index.json` entry with no corresponding `unpacked/` directory is the one case `--offline` still verifies and unpacks before answering, because it has not yet produced a `verified.json` record of its own.
- Writing a lock for **every platform the index offers**, not only the host's own, downloads and verifies every platform's bundle but fetches the **layer only for the host's own platform** — `lock-write-all-platforms` asserts zero layer `GET`s for non-host platforms.

## 7. The retry table

5 attempts, first wait 4s, ×2 each time; retry on 408, 429, 500, 502, 503, 504; honor `Retry-After` on 429, 503; a `Retry-After` past the remaining budget is refused rather than shortened, and the refusal names the value.

A digest 404: `next_base_then_retry_on_last`. A tag 404: `next_base_then_unpublished`.

## 9. The seam

The fetch layer is a module with exactly four entry points, identical across all four bindings (spelled per that language's own naming convention) and called from nowhere outside the module except the binding's own loader, once the FFI lane wires it in:

- `ensure(request, options) -> Resolved` — may use the network unless `offline`.
- `resolve_installed(request, platform, options) -> Resolved | MISS` — **never touches the network**; what a loader calls on every `open`.
- `list_installed(options) -> [Resolved]`, `verify_installed(options) -> [VerifyResult]`.
- `fetch_signed(repository, ref, predicate_type, options) -> {path, statement, digests}` — the generic signed-artifact fetch goldens and fixtures reuse, so neither needs its own trust logic.

A `Resolved` carries: `abi_generation` (always 1); `platform`, `request`, `version`, `channel` (from the predicate, when present) and `build`; `library_path` (absolute) and `dir` (`<layout>/unpacked/sha256/<manifest-hex>`); `digests {index?, manifest, layer, bundle, bundle_manifest?}`; the verified `predicate` object verbatim (including `abi_fingerprint`, `library_sha256`, `library_bytes` and `glibc_floor`); `signed_by` (the key id, or `""` under allow-unsigned); `source` (a base URL, `cache`, or `system:<dir>`); `already_installed`; and `warnings[]`.

**On return, the fetch layer guarantees:** the library file exists and its sha256/size equal the signed predicate's; the predicate verified under a trusted key (or allow-unsigned was explicit and loud); `predicate.abi == abi_generation`; the predicate's `os`/`arch` equal the request's platform; the predicate's version lies within (or equals) the request.

**The fetch layer never:** `dlopen`s anything; interprets `abi_fingerprint` (passed through opaque); checks glibc; or reads a `chs_*` symbol. Those checks — and the `CHTYPES_ARTIFACT_INCOMPATIBLE` error code they can raise (§8) — belong to the FFI/loader lane, not yet built as of this writing (blocked on the ABI v1 design, core issue #647). When it lands, it calls `resolve_installed` and `ensure` exactly as any other caller of this module would; the seam above is frozen specifically so that lane can be written against it without this module changing underneath it.

## 10. Conformance

Every fixture under `tests/fixtures/fetch-v1/` — route trees, OCI image layouts, scripted HTTP responses, locks and `cases.json` itself — is generated by `scripts/fetch-v1/genfixtures/` (its own Go module; `cd scripts/fetch-v1/genfixtures && go run . --write`), except `tests/fixtures/fetch-v1/{test-key,other-key}/` (hand-generated ed25519 keys, read but never written by the generator) and `tests/fixtures/fetch-v1/layouts/oras-preseed/` (written only by a real `oras copy -r --to-oci-layout`, in the `v1-oras-preseed` workflow job). The generator is deterministic — no timestamps, no randomness — so `go run . --check` (regenerate into a temp directory and diff) is the drift gate, and `go run . --selftest` proves that gate actually catches drift, on a throwaway copy.

### Running the suite locally

```bash
cd scripts/fetch-v1/genfixtures && go run . --write   # regenerate every fixture
python3 scripts/fetch-v1/schema_check.py               # validate cases.json, http/*.json, locks/expected/*.json
python3 scripts/fetch-v1/server.py --fixtures "$(pwd)/tests/fixtures/fetch-v1" --port 0
python3 scripts/fetch-v1/parity.py --reports-dir <dir-of-report-*.json>
```

`server.py` prints `LISTENING <port> <port2>` once it is ready: `<port>` is the primary origin every HTTP-transport case's `{base}` expands against, `<port2>` is a second origin used only by cross-origin-redirect cases. The server runs until killed; a conformance runner starts one instance, runs every HTTP-transport case against it, and reads `GET /_log/s-<case-id>` afterward for whatever its own assertions need from the raw request log (headers included) that a `cases.json` `expect` field has no room for — see "Known gaps" below.

### The runner contract

Each binding ships one runner, gated on `CHTYPES_V1_CONFORMANCE=<abs path to tests/fixtures/fetch-v1>` (unset: skip loudly by name, never a silent pass). It executes every case on every transport `cases.json` lists for it, starting `scripts/fetch-v1/server.py` itself for any case listing `http`. The exact commands `v1.yml`'s `v1-conformance` matrix runs (plan §3.3, frozen; none of these per-binding test files exists yet, so none is cited here by path — each binding lane adds its own): Go, `go test -count=1 -run '^TestConformanceV1$' ./internal/ocifetch/`; Python, `uv run pytest -q` on its own `ocifetch` conformance module; TypeScript, `pnpm exec vitest run` on its own `ocifetch` conformance spec; Rust, `cargo test --features fetch-v1 --test ocifetch_conformance`. CI runs each of them with no network but loopback, in a network namespace entered for that process tree alone (`scripts/fetch-v1/sandbox.sh`, which also proves itself with `--selftest` on every pull request): a runner that needs the internet fails there, not on a user's machine.

**`{base}` per transport** (§2, §4): `file://<abs>/tests/fixtures/fetch-v1/trees/<tree>/v2/chtypes/v1`; `http://127.0.0.1:<port>/s-<case-id>/chtypes/v1` (a conformant client always splices its own `/v2/` in immediately after the scheme and authority, the same place a real repository name sits — `default_bases` in `constants.json` has no `/v2/` in it either, for the same reason — so the full wire path becomes `/v2/s-<case-id>/chtypes/v1/...`, which is exactly what `server.py` parses); `https://registry.test:5443/chtypes/v1` (the `v1-network` job's own `registry:2`).

**`{base2}`** (http transport only; decided here, lane 0B, 2026-10-02): the same `s-<case-id>/chtypes/v1` suffix as `{base}`, but rooted at `server.py`'s SECOND origin — the second port on its `LISTENING <port> <port2>` line — for a case that needs two genuinely independent bases over the same case id, such as a mirror-failover case (`mirror-failover-5xx`, `mirror-failover-digest-404`): base[0]'s scripted failures exhaust against `routes`, base[1] (`{base2}`) is served from that same script's `second_origin_routes`, with its own response-sequence cursor (`server.py` keys its cursor on `(case id, origin, method, path)` precisely so a second-origin route never shares state with the first-origin route of the same path).

**Writing `CHTYPES_V1_REPORT`** (`report.schema.json`): one JSON file per toolchain leg, `{"schema":1,"binding":"go","toolchain":"go1.27.x","cases_sha256":"<sha256 of the head's cases.json>","results":[{"id":...,"transport":...,"verdict":"pass"|"fail","detail":"..."}]}`. The `v1-network` job's own report (registry-transport results only, for the five cases below) uses the toolchain value **`"registry"`** — a sentinel `parity.py` recognizes; it is never one of the matrix's real per-binding toolchain strings. Every report is uploaded `if: always()`, named `report-<binding>-<toolchain>.json`, whether its job passed or failed — `v1-parity` needs to see a _missing_ report as distinct from one that ran and failed.

**`CHTYPES_V1_TOOLCHAIN`** names the report's `toolchain` field exactly as the matrix and `parity.py` spell it (`go1.27.x`, `3.13`, `node24`, `1.87`, ...). `v1.yml` exports it from the matrix leg (`registry` in the `v1-network` job); a runner uses it verbatim when set and falls back to its own mapping of its runtime version otherwise. A runtime's own patch version (`go1.27.1`) is rejected by `parity.py`.

**The registry report.** The runners take no registry-only switch: with `CHTYPES_V1_REGISTRY_BASE` set they run every transport. The `v1-network` job therefore keeps only the `registry` rows of each runner's raw report and writes them as `report-<binding>-registry.json` with `toolchain` `registry`; the file and http rows are judged by the `v1-conformance` legs. The job's `registry:2` is loaded by `scripts/fetch-v1/push_tree.py` with every tree a registry-transport case names. TLS is never configured per binding: the throwaway CA is installed in the OS store and each binding must trust it from there (Node via its documented `--use-system-ca` option).

**Enrollment:** add `spec/fetch-v1/enrolled/<binding>` (an empty file) in your own binding's PR, never another's. `parity.py` refuses a run where the enrolled set has shrunk since `v1`'s own tip.

### How to add a case

1. Add it to the relevant `scripts/fetch-v1/genfixtures/*cases.go` file (grouped the same way `cases.json`'s id ranges already read: `resolve.go`, `trust.go`, `bytescases.go`, `cachecases.go`, `lockcases.go`, `httpcases.go`, `genericcases.go`), building whatever tree/layout/http-script fixture it needs with the shared helpers in `artifact.go`/`tree.go`/`layout.go`/`sign.go`/`tarzstd.go`.
2. `go run . --write`, then `python3 scripts/fetch-v1/schema_check.py` and `go run . --check` (twice — the `v1-fixtures` job's own gate).
3. If the case is HTTP-transport, extend `server.py`'s selftest or at least smoke-test it directly against the regenerated fixtures (every special-cased script id in `server.py`'s own header comment is a precedent for what needs bespoke server logic versus a purely declarative `http/<id>.json`).
4. Every case id must be unique across every category file (`checkUniqueIDs` in `cases.go` panics otherwise); every array/object field must be non-nil even when empty (`[]`, never `null` — `cases.schema.json` types every one of them as a bare array or object).

### The generic-fetch convention

A case id starting `goldens-` or `fixtures-` exercises `fetch_signed(repository, ref, predicate_type)` (the seam, §9) instead of `ensure()` — not a separate case shape (lane 0A's `cases.schema.json` has none, and extending the frozen contract is not this lane's call to make). `request.spelling` carries the bare `sha256:<hex>` ref to resolve — a goldens referrer's own manifest digest, or (for `fixtures-digest-pin-no-tag-fallback`) the SDK's own fetch-fixtures artifact's manifest digest in its own repository (`chtypes/v1/sdk-fetch-fixtures`) — and `expect.manifest`/`expect.library_sha256` name that artifact's own digest and content hash, never a platform manifest's.

### Cache fixtures and `installed.json`

A `layouts/<name>/` fixture (`setup.cache` names one) is always a plain OCI image layout — `oci-layout`, `index.json`, `blobs/sha256/<hex>` — the same shape a real `oras copy --to-oci-layout` produces. **It never carries a pre-populated "already unpacked" record.** That bookkeeping (§1's `verified.json`) is each binding's own internal, implementation-private format; it is not part of the frozen seam (§9 only returns a `Resolved` value, never a file format) and this generator never fabricates one. Every binding's fetch layer must already treat a pre-seeded `index.json` entry with no corresponding `unpacked/` directory as unverified — verify-then-unpack from local blobs, zero network — so most cache cases (`offline-hit`, `offline-miss`, `preseed-oras`, `system-dir-readonly`) need nothing more than the layout itself.

**`preseed-oras` is CONDITIONAL on `layouts/oras-preseed/` actually being on disk, checked fresh on every `--write`/`--check`/`--selftest`.** That directory is written only by a real `oras copy -r --to-oci-layout` in the workflow_dispatch-only `v1-oras-preseed` job, never by this generator — and as of this writing that job has not yet landed its output in this tree. Rather than ship the case unbacked (a `setup.cache` naming a directory that cannot exist, which every binding's runner would either 404/ENOENT on or have to special-case around — a GENERATOR problem presented as a binding one, the exact defect three fetch lanes independently found, 2026-10-02), `cachecases.go` gates the case's very presence in `cases.json` on `layoutPresentOnDisk("oras-preseed")` and otherwise skips it LOUDLY (a stderr line, every run, never silent — the same discipline `CHTYPES_V1_CONFORMANCE` unset already follows, above). Dispatching the job and committing its output is enough to pick the case back up on the next regeneration; no binding needs a second wiring pass. `checkCacheLayoutsExist` (`cases.go`) is this same invariant's second, independent check.

Three cases (`existing-install-noop`, `monotonic-warning`, `offline-newest-of-two`/`offline-newest-build`) need something to already be **installed**, not merely present, before the case begins. For these, the layout root also carries `installed.json`: `{"installed": ["sha256:<manifest digest>", ...]}` — a **test-setup instruction for the conformance runner**, read before the case starts ("call your own `ensure()`/unpack path against exactly these manifest digests, offline, from these local blobs, before starting the clock"), never a file any binding's shipped cache code parses at runtime. This is a decided-here convention (lane 0B), not part of lane 0A's frozen contract.

**`existing-install-noop`'s assertion is "zero LAYER requests," not "zero requests at all."** The case is ONLINE, not `--offline` — the manifest and signature bundle may legitimately be re-resolved over the network to confirm the already-installed build is still the one the line now offers — so `expect.requests.max` is not the right shape for it. What must never happen is a `GET` for the layer blob itself, since the already-installed bytes already satisfy it: `expect.requests.none_matching` names exactly that one path, `["GET .*/blobs/<layer digest>"]`, scoped to the layer only. (This case and `index-race-reapply`, alongside it in `cachecases.go`'s "cache" tree, originally published their manifests under a `c-<id>`-shaped symbolic tag instead of their own version spelling — so `index-race-reapply`, which never resolves `--offline`, could never find a tag to resolve against at all, and `existing-install-noop` likewise. Fixed here, lane 0B, 2026-10-02 — tagged under their real version spellings now, with `checkOnlineTagsExist`, genfixtures' own generator self-check, panicking on any future case shaped the same way.)

### `layouts/basic` and the registry job

`layouts/basic/` is the one layout `v1-network` pushes into `registry:2` whole: its root entry is the full multi-platform **index** for tag `26.8.15.10` (every platform fans out from it), matching what a real push publishes. Every other layout in this tree roots at ONE platform's manifest directly (the shape a real `oras copy --platform <p> --to-oci-layout` produces) — **measured locally, oras 1.3.4: a layout with several same-tagged single-platform root entries resolves ambiguously, to just one of them**, which is why `layouts/basic` is built differently (`copyIndexIntoLayout` in `layout.go`, not `copyArtifactIntoLayout`).

**Also measured locally (oras 1.3.4):** `oras cp -r --from-oci-layout` does **not** copy referrer artifacts from a local OCI layout source — `-r`'s referrer discovery goes through the Referrers API (or the fallback-tag convention), neither of which a plain directory implements. The `v1-network` job's push step therefore moves only the index and its platform manifests; a following step attaches the linux-arm64 signature bundle directly (`oras attach`, reading the bundle bytes straight from the tree fixture) so the job's own "record registry:2's referrers behavior" step has something real to observe. This is a gap in `oras`'s layout-source support, not in `registry:2` or in this fixture — a real producer push (blocked on the delivery side, plan §1.2) will use its own mechanism and is not expected to hit it.

**`registry:2`'s referrers behavior — measured, CI run 36965426062, job "v1-network," 2026-10-02** (both GETs sent the `Accept` header `manifest-accept-header` already requires; the first measurement, without it, read the fallback tag as absent when it was only unnegotiated): `GET /v2/chtypes/v1/referrers/<digest>` answers a real `404 page not found` — this stock `registry:2` image does not implement the referrers API — but `GET /v2/chtypes/v1/manifests/sha256-<hex>` answers `200` with `{"schemaVersion":2,"mediaType":"application/vnd.oci.image.index.v1+json","manifests":[{...,"artifactType":"application/vnd.dev.sigstore.bundle.v0.3+json"}]}`, naming the pushed signature bundle exactly. `oras attach`'s default (`--distribution-spec unknown`) writes that fallback tag itself once it detects the referrers API is absent, so every `no-referrers-api-uses-fallback-tag`-shaped host this job can reach is in fact discoverable, just not through the API half.

### Known gaps (report these against this guide, not against a case's `ok`/`code`)

- **`download-token-sent`, `manifest-accept-header`:** `cases.schema.json` has no field for "this header must have been sent" — only `requests.none_matching` (absence). Both cases are enforced by `server.py` itself refusing (400/second 401) when the required header is missing or wrong, which is why they have no declarative `http_script` response sequence doing the real work; see `server.py`'s own header comment.
- **`spelling-refused`/`spelling-refused-v-prefix`:** refused before any network call, by a client-side regex check, which is not one of the ten shared error codes (`errors`, above) — `expect.code` is `null` for these two; `expect.requests.max: 0` is the real assertion.
- **The `hint` field of every bundle this repository signs is our own keyid** (the `sha256-first16hex` scheme every binding already computes for v0), never a raw-key encoding. Nothing in layout-v2 spec §4.2 fixes the hint's content beyond "a public-key hint" — none of this repository's four hand-rolled verifiers select a key BY the hint (they try every trusted key), so the format is this generator's own choice, recorded here so a reference-verifier integration (`scripts/fetch-v1/refcheck/`) keys its own trust mapping by the same string.
- **`scripts/fetch-v1/refcheck/` is a representative sample, not an exhaustive cross-check.** It verifies a handful of known-good bundles (one per predicate type this repository signs anything with) against sigstore-go, `@sigstore/verify` and `cosign verify-blob-attestation`, report-only. The plan's broader vision — cross-checking every fixture's trust verdict against all three reference verifiers — is future work, not this lane's acceptance bar.
- **sigstore-go: the delivery side's design doc cites version "1.3.0"; that version does not exist on the Go module proxy as of 2026-10-01** (the newest published tag is v1.2.2, which `refcheck/go` pins and which verifies this repository's bundles). Recorded here rather than silently substituted.
- **Every referrer manifest's config blob must physically exist, not only be embedded via the descriptor's `data` field.** Measured against a real registry host (the artifact producer's own push of `trees/basic`, 2026-10-02): a manifest PUT whose config digest has no backing blob is refused `400 BLOB_UNKNOWN`, `data` field or not. `genfixtures` registers the `{}` empty config (`sha256:44136fa355b3678a1146ad16f7e8649e94fb4fc21fe77e8310c060f61caaff8a`) as a real blob in every tree and layout that has a referrer manifest, alongside the embedded `data` convenience.
- **`missing-platform`'s partial tag (`26.6`, linux-amd64 and linux-arm64 only, darwin-arm64 omitted) is checked against the real host's behavior.** The real host never serves a partial set at all (an incomplete line's tag is a 404, not a 200 with a short index), so this fixture's WIRE SHAPE differs from the real host's — but no case requests a platform the partial tag _does_ carry expecting success, so the client-observable outcome (the requested platform is unavailable, `CHTYPES_ARTIFACT_UNPUBLISHED`) matches either way. Confirmed by grep (`command grep -n "26\.6" scripts/fetch-v1/genfixtures/*.go`): `26.6` is cited exactly once, as `missing-platform`'s own tag, requesting the platform it omits.
- **Follow-up, not done in this change:** the real host's index JSON is compact with a different key and platform order than this generator's (indented, insertion order); layout-v2 spec §5.1 now pins the host's canonical form. Locks pin whichever digest they actually receive, so nothing here is broken by the difference — but a later change should regenerate every fixture index in that canonical form so fixture digests match the host's byte-for-byte, which would also let a future cross-check diff fixture bytes against a live pull directly.
