# Fetching, verifying and installing v1 artifacts — the OCI contract every SDK implements

> **Status: live.** This is the fetch contract every 1.x binding implements; the 0.x release directory and signed `SHA256SUMS` are retired. This page is the normative contract for the v1 fetch layer: an OCI registry, zstd-compressed layers, and a key-based Sigstore bundle per platform manifest, replacing today's release directory and `SHA256SUMS`. Where this page and the delivery side's `layout-v2` design disagree, that design's own §0 wins, and this page is a bug until it is corrected.

Four thin per-language fetchers share one wire contract: resolve a floating or exact version against an OCI registry, verify a signed statement that binds the platform, the version and the ABI generation to the bytes, then unpack and cache the result. No SDK speaks both v0 and v1; the switch (§2.4 of the plan) is a clean cut, not a fallback. The 0.x shell fetcher is retired with 0.x and not replaced — every binding fetches for itself.

The source of truth for every value this page cites is [`spec/fetch-v1/constants.json`](../../spec/fetch-v1/constants.json), generated by [`scripts/fetch-v1/gen-constants.py`](../../scripts/fetch-v1/gen-constants.py) into all four bindings and into the reference table below. Nothing in this page repeats a value the generator does not also produce — a number quoted twice is a number that can drift, so §7 and §8 are generated, never hand-typed.

## 1. The cache

A standard **OCI image layout** rooted at `${XDG_CACHE_HOME:-~/.cache}/chtypes/v1/` (`CHTYPES_CACHE` names the layout directory itself, overriding the whole path, not a parent of it). This is a v1-only root: it shares nothing with v0's `…/chtypes/artifacts/abi<R>/` caches or with a developer's local build caches under `…/chtypes/` — a fetch here never reads or writes either.

- `oci-layout`, `index.json` and `blobs/sha256/<hex>` are the OCI image layout proper: every manifest, index and layer blob this fetcher has verified, content-addressed.
- `unpacked/sha256/<manifest-hex>/` sits beside `blobs/`: the unpacked library for one verified platform manifest, named by that manifest's own digest. A `verified.json` record inside it is the durable proof that this directory was verified once, under which key, and against which digests — **the source of truth for `--offline` and `resolve_installed`** (never `index.json`; see below). The record has one format, below, which every binding writes and reads: the cache is shared, so a cache one binding wrote is a cache every binding reads.
- `index.json` is written by **temp-file-then-atomic-rename**, then re-read and re-applied, never edited in place — two concurrent fetches racing the same cache must both survive (the `index-race-reapply` case, §10).
- An `unpacked/sha256/<manifest-hex>/` directory is installed by **renaming a complete temporary directory**, its library and its `verified.json` already written, into place. The rename comes first, so when several processes of any binding install one build into one cache at once, the first wins and the rest keep its entry. An entry that holds an acceptable record is never removed or replaced, because another process may be using it. Only an entry without one (§1, below) is moved aside, into a fresh `.stale-*` directory beside it, and replaced; if it turns out to hold an acceptable record after all, it is put back. A reader lists only `<manifest-hex>` names, never an installer's temporary directory. Every temporary and aside name carries random bits drawn in its own process, never a clock reading alone, so no two writers ever pick the same one. The `v1-cache-interop` job runs eight concurrent installs for each binding alone and for all four mixed, with a watcher for torn, vanished and replaced entries (public issue #482).
- Read-only **system directories** are never written to, and they and the user cache are **one search**: `resolve_installed`, `list_installed` and `verify_installed` read the cache, then every system directory in order. Among all the records that answer a request, the newest (version, build) wins, and a tie goes to the earlier root. Only when no root holds such a record is a pre-seeded entry installed, from the roots in the same order (§6). The `root-order-*` cases (§10) pin this in every binding (public issue #486).
- **Where the lookups read is public.** The cache root and the ordered search directories are an API in every binding, and the same answer the lookups above use, so an embedder never copies the precedence (public issue #530): Go `chtypes.CacheRoot(FetchOptions)` and `chtypes.SearchDirs(FetchOptions)`, Python `chtypes.cache_root(options)` and `chtypes.search_dirs(options)`, TypeScript `cacheRoot(options)` and `searchDirs(options)`, Rust `chtypes::cache_root(&options)` and `chtypes::search_dirs(&options)`. The root is the explicit cache directory, else `CHTYPES_CACHE`, else `${XDG_CACHE_HOME:-~/.cache}/chtypes/v1`; the search directories are that root, then each system directory (`system_dirs`, else the built-in list, `[]` for none) in the order above. Both are absolute: a relative explicit directory or `CHTYPES_CACHE` is resolved once against the process working directory (lexically: `.` and `..` fold, no symlink is followed), the same in all four bindings, so a `Resolved`'s `dir` and `library_path` are absolute too (public issue #541). Neither creates a directory or reads one. `chtypes where` still prints the root alone; `chtypes where --all` prints the search directories, one per line, the root first, identically in all four CLIs. The `tests/fixtures/cache-roots/cases.json` table is read by all four bindings' tests, so each gives one list for the same environment and options. A 2.0.0-dev SDK answers the same way through the dev channel's subroot: the root is `<explicit directory or CHTYPES_CACHE>/v2-dev`, or `${XDG_CACHE_HOME:-~/.cache}/chtypes/v2-dev`, and the built-in system directories are the `v2-dev` ones (`spec/abi-v2/docs.md`, rule r5).
- **Modes follow the umask.** Every directory and file the fetch layer creates is created with mode 0777 or 0666, and the process umask alone takes bits away, the temporary file or directory renamed into place included. At the usual umask 022 a cache one uid writes is readable by every other uid (a CI user and a container's nonroot user, for example), and readable is never writable: everything in the cache was downloaded anonymously and is signature-verified, and the library is re-hashed against its record at load. umask 077 keeps a private cache, and umask 002 with a setgid root gives a group-writable one. No binding has a mode option; the umask is the one knob (public issue #486).
- The cache **can be pre-seeded** with `oras copy -r --to-oci-layout` (ORAS 1.3.4 and `--platform` are `measured` compatible with this layout, per the delivery side's design). A pre-seeded layout has entries in `index.json` with no corresponding `unpacked/` directory yet; the first request for one verifies it against its signature exactly as a freshly downloaded layer would, then unpacks it. Losing a pre-seed's `index.json` entry to a losing race costs only `oras` interop, never correctness — verification never trusts `index.json` content, only digests it then independently checks.

### The cache faults

Every fault the fetch layer can meet in a cache root is one of five kinds, and each binding answers each kind the same way (public issue #486):

| kind                                                                                                                          | example                                   | default mode                                                                 | strict mode                                                                                |
| ----------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------- | ---------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| K0, a missing root                                                                                                            | a fresh volume path not yet created       | absent; a fetch creates it                                                   | the same: a missing root is the empty cache, not a fault                                   |
| K1, an unusable root: the root or `unpacked/sha256/` exists but cannot be listed, or is not a directory                       | a mode 000 mount; the path is a file      | absent, plus a warning naming the path                                       | `CHTYPES_CACHE_UNUSABLE`, reason `unreadable_root` or `not_a_directory`                    |
| K2, an unreadable entry: an entry directory or its `verified.json` exists, and opening it fails with anything but "not found" | an entry another uid wrote 0700 or 0600   | absent, plus a warning naming the path                                       | `CHTYPES_CACHE_UNUSABLE`, reason `unreadable_entry`                                        |
| K3, an unacceptable record                                                                                                    | a garbage record; another schema          | absent: re-verified from the blobs and replaced, as below                    | the same, and only when there are no blobs to re-verify from, reason `unacceptable_record` |
| K4, a 0.x layout: no `oci-layout`, no `unpacked/`, and a `<minor>/manifest.json`                                              | `CHTYPES_CACHE` pointed at a 0.x registry | absent, with the 0.x hint on the not-installed answer ("Upgrading from 0.x") | `CHTYPES_CACHE_UNUSABLE`, reason `layout_0x`                                               |

- **A missing `oci-layout` is not K4 by itself.** Python writes none, and an `oras` pre-seed does. K4 needs the positive 0.x shape, and a root with `unpacked/sha256/` is a 1.x cache whoever wrote it.
- **The default mode keeps "unreadable is absent"**, so a deployment that works today works the same. It gains one warning per K1 or K2 path, per call: `<path> could not be read (<errno>); treated as not installed. Set CHTYPES_CACHE_STRICT=1 to make this an error.` The warning is in `Resolved.warnings` when a build is returned, and in the not-installed answer's message when none is; the CLI's `list` and `verify` print it on stderr.
- **Strict mode** is opt-in: Go `FetchOptions.StrictCache`, Python `FetchOptions(strict_cache=)`, TypeScript `FetchOptions.strictCache`, Rust `FetchOptions::strict_cache`, else `CHTYPES_CACHE_STRICT=1` (`0` is off), else off, and `--strict` on every CLI command. It checks the cache before any system directory is consulted, so a fault in the cache is raised and nothing falls through. A system directory that does not exist is skipped, as a default list is; one that exists but is unusable (K1 or K2) is an error too. It applies to `resolve_installed`, `list_installed`, `verify_installed` and `ensure` alike, and an online `ensure` checks the cache before it fetches into it. `chtypes where --strict` checks the root before printing it, and `chtypes verify --strict` that verified no build exits with `CHTYPES_ARTIFACT_MISSING`, so a mounted cache can be health-checked. Strict by default for an explicit cache is a later, separate decision.
- **`CHTYPES_CACHE_UNUSABLE` (exit status 9, §8)** names the exact path, the reason and the errno name (`EACCES`), and its message is the same sentence in every binding: `<path> is unusable as a cache: <reason> (<errno>)`. Its sixth reason, `unwritable`, applies in every mode: a write the fetch layer needed (a directory, a temporary file, a rename) failed under the cache. That replaces what each binding raised before: Go a misuse error, Python a raw `OSError`, TypeScript a misuse error, Rust `CHTYPES_SOURCE_UNREACHABLE`.
- The `v1-cache-interop` job faults every binding's cache seven ways (none, the root 000, `unpacked/sha256` 000, an entry 000, a record 000, a garbage record without blobs, a 0.x registry) and requires every binding, reading as another uid, to give the same answer in both modes, with and without a system directory holding the build. Its ABI v2 matrix repeats the faults over the 2.0.0-dev CLIs and the staging registry, with the cache under the `v2-dev` subroot (so the root is faulted at the cache directory and at the subroot, eight faults in all), on linux-amd64 as the required check and on linux-arm64 and darwin-arm64 as separate, unrequired ones (public issue #558).

### The `verified.json` record (schema 1)

The schema is `spec/fetch-v1/schema/verified.schema.json`. The record is a JSON object with exactly these members, every one present, with `null` where shown:

```json
{
  "schema": 1,
  "platform": "linux-arm64",
  "version": "26.8.15.10",
  "channel": "lts",
  "build": "20261001.183455",
  "library": "libchtypes.so",
  "library_sha256": "<64 lowercase hex>",
  "library_bytes": 123456,
  "digests": {
    "index": "sha256:<hex>",
    "manifest": "sha256:<hex>",
    "layer": "sha256:<hex>",
    "bundle": "sha256:<hex>",
    "bundle_manifest": "sha256:<hex>"
  },
  "signed_by": "<key id>",
  "predicate": {}
}
```

- `platform` is `linux-amd64`, `linux-arm64` or `darwin-arm64`. `version` is the exact four-part version and `build` the fixed-width build timestamp, both from the verified predicate. `predicate` is the verified statement's predicate, verbatim.
- `library` is the library's file name **relative to the unpacked directory**: never an absolute path, never a path with a separator, never `.` or `..`, so a cache that moves still reads. `library_sha256` and `library_bytes` are what the installer measured on the unpacked file (equal to the signed predicate's).
- `channel`, `digests.index`, `digests.bundle`, `digests.bundle_manifest` and `signed_by` may be `null`. `signed_by` and `digests.bundle` are `null` only under allow-unsigned. `digests.index` and `digests.bundle_manifest` are informational: `null` when the install path never saw them (a frozen install never saw the index).
- A reader ignores any member not listed here and never refuses a record for one.

**Writers** write exactly this object, atomically (a temporary file in the same directory, then a rename of the directory or file), once per directory. Key order and whitespace are free; what is equal across bindings is the parsed members.

**Readers** accept exactly `schema` 1. A record that is missing, unparsable, of another `schema`, or that breaks a rule above is treated as **ABSENT**, never as a failure by itself and never trusted: the directory is re-verified from the cache's own content-addressed blobs, exactly as a pre-seeded `index.json` entry is (a failing re-verify is the usual `CHTYPES_ARTIFACT_CORRUPT`; no blobs at all is not installed). After a successful re-verify the unreadable directory is replaced by the freshly verified one (a temporary directory in the same parent, then a rename), so the record that could not be read is gone and the next reader finds a good one. The conformance cases `cache-record-*` (§10) prove this in every binding, and the `v1-cache-interop` job proves that a cache any binding writes is read by every binding, that a cache holding two lines answers each line's request with that line in every binding, that the read-only commands create nothing, and that a cache any binding writes at umask 022 is read by every binding as another uid (`nobody`, through `sudo`).

### Upgrading from 0.x

`measured` (from the source on this branch): every v1 binding resolves its cache root to `${XDG_CACHE_HOME:-~/.cache}/chtypes/v1/`, or to `CHTYPES_CACHE` when set (`expandCacheRoot` in `go/internal/ocifetch/ensure.go`, `resolve_cache_root` in `python/src/chtypes/_ocifetch/_layout.py`, `cache_root` in `rust/src/ocifetch/layout.rs`, `cacheRoot` in `ts/src/ocifetch/layout.ts`). The 0.x line used a different root: a registry directory of `<minor>/manifest.json` entries, by default `${XDG_CACHE_HOME:-~/.cache}/chtypes/artifacts/abi<R>/<os>-<arch>/`, set by the retired `CHTYPES_REGISTRY` (the 0.x Go and Python registry code and the 0.x fetch guide's §1, all three retired with 0.x and kept in the 0.x release history). `inferred`: the TypeScript and Rust 0.x registries use the same layout, as that guide stated it for all four. So a machine that carries a 0.x cache into 1.0 has two disjoint directories, and nothing in 1.0 reads or writes the old one.

Nothing about a 0.x cache may crash 1.0, including when something points the 1.0 root at it:

- A `CHTYPES_CACHE` that names a 0.x registry directory (no `oci-layout`, no `index.json`) is an empty, foreign layout. A fetch proceeds normally and installs beside the old files without touching them. `--offline` and `resolve_installed` answer the ordinary not-installed code. Nothing is read as verified. (`upgrade-0x-registry-*`.)
- That not-installed answer names the directory, in every binding and in the registry's own miss alike: `<root> holds a 0.x registry (<minor>/manifest.json); chtypes 1.x uses an OCI layout at ${XDG_CACHE_HOME:-~/.cache}/chtypes/v1 — point CHTYPES_CACHE at an empty or 1.x directory.` A `chtypes verify` of the directory prints the same sentence. The shape is positive: no `oci-layout`, no `unpacked/`, and at least one `<minor>/manifest.json` (the first by name). A missing `oci-layout` alone is not the shape, because a Python-written 1.x cache has none, and a directory with `unpacked/` is a 1.x cache whoever wrote it (public issue #486). In strict mode the directory is `CHTYPES_CACHE_UNUSABLE` with reason `layout_0x` instead, for an online fetch too (§1, the cache faults).
- An `unpacked/sha256/<hex>/` directory holding a 0.x-style `manifest.json` and no `verified.json` reads as absent. It is re-verified from blobs when they exist and reported not installed when they do not. (`upgrade-0x-unpacked-*`.)

## 2. Sources

- **Base URLs** are an ordered, repository-qualified list (`https://registry.wavehouse.dev/chtypes/v1` by default; `CHTYPES_ARTIFACTS_URL`, comma-separated, replaces it). A mirror's repository path may differ (for example a GHCR mirror), which is why a base names the whole repository root, not just a hostname.
- Bases are tried **in order on a temporary error** (a timeout, a 5xx, a connection refusal) and **never on a verification failure** — a base that serves a byte-for-byte wrong artifact is a fault to report, not a reason to go shopping for a base that will lie more conveniently.
- **No hostname pinning.** Trust comes entirely from the signature (§4); any base, including a third-party mirror, is equally trusted once its bytes verify.
- `HTTPS_PROXY`/`NO_PROXY` and the system certificate store are honored by every binding's own HTTP stack (`net/http`, `urllib.request`, Node's `https`/`http` with `tls.getCACertificates`, `ureq`'s platform verifier) — never a bespoke TLS or proxy implementation.
- `CHTYPES_DOWNLOAD_TOKEN`, when set, is sent as `Authorization: Bearer <token>` to the configured base hosts only (exact host match), **never forwarded across a redirect**, and never required by the default host.
- **Redirects** are followed up to `limits.max_redirects` hops, with `Authorization` dropped on any cross-origin hop. The default host never redirects a blob GET (it serves bytes directly); a mirror may, so the handling stays in every binding regardless.
- **User-Agent.** Every HTTP request a binding's fetch layer makes (manifests, blobs, referrers, `tags/list`, anonymous-token exchanges, and every redirect hop followed) carries exactly `User-Agent: chtypes-<binding>/<version>`, where `<binding>` is `go`, `python`, `ts` or `rust` and `<version>` is that binding's own package version (`0.0.0-dev` when it cannot be determined; the header is never omitted). The string matches `^chtypes-(go|python|ts|rust)/[0-9A-Za-z.+-]+$` and carries nothing else. Delivery hosts may refuse a generic library agent (`measured`: the default delivery zone answers `Python-urllib/3.13` with a 403 from its browser-integrity check and `chtypes-python/<version>` with a 200), so no binding may send its HTTP stack's default. Each binding builds the header in one helper that every request path uses. The conformance fixture server (`scripts/fetch-v1/server.py`) answers `400` to any request whose agent does not match the pattern and records the agent in its request log, so a binding that omits it fails every http-transport case.
- `CHTYPES_REGISTRY` (the v0 variable) is **retired**: set, it produces exactly one loud warning and is otherwise ignored. `CHTYPES_ARTIFACTS_URL` is v1's equivalent.

## 3. Resolve

`GET /v2/<repository>/manifests/<tag>` for the requested spelling (a two-, three- or four-part version) returns a multi-platform **OCI image index**. The fetch layer:

1. selects the descriptor for the running platform (`os`/`architecture`); no match is `CHTYPES_ARTIFACT_UNPUBLISHED`, naming what the index actually offers;
2. `GET`s that platform's manifest **by digest**, and verifies the fetched bytes' sha256 and size against the index descriptor before parsing anything inside it;
3. reads the manifest's own layer descriptor (exactly one layer: the library tarball) and config descriptor, without yet trusting either — trust is established in §4, never assumed from shape.

An index, manifest or layer whose media type the fetch layer does not recognize is `CHTYPES_SOURCE_INCOMPATIBLE` — a protocol-shape problem, never a trust problem. The version spelling itself is checked against `spelling.regex` **before any network call**; a `v`-prefixed or channel-suffixed spelling (`v26.8`, `26.8.15.10-lts`) is refused immediately with a hint naming the v1 spelling (`spelling.refuse_hint_regex`).

## 4. Trust

Each platform manifest's signature is one or more **Sigstore bundle v0.3** referrers (`application/vnd.dev.sigstore.bundle.v0.3+json`), found through the OCI **referrers API** (`GET /v2/<repository>/referrers/<manifest digest>`, filtered by `artifactType`) or, when a host does not serve that API (a mirror may not), the **fallback tag** `sha256-<hex>`. Both are implemented in every binding — never only one, because which a given host serves is a property of that host, not of this fetcher.

**A manifest can carry several referrers of the signature artifactType at once** — a key rotation adds a **second** bundle rather than a second signature inside one envelope (§0 of the delivery side's design) — and a manifest also carries a separate goldens referrer (one per platform manifest, D7) with its own artifactType. The fetch layer therefore:

- always filters referrers by `artifactType` itself, never assuming a referrers listing holds only one kind of object;
- accepts the manifest's signature as soon as **any** referrer of the signature artifactType verifies under a trusted key — it does not require every bundle present to verify, and it does not stop at the first bundle that fails to.

Verifying one bundle:

1. parse the bundle JSON;
2. compute the DSSE envelope's **pre-authentication encoding (PAE)** over the payload;
3. verify one ed25519 signature against the trusted key list, using the primitive each binding already ships for v0 (Go `crypto/ed25519`, Python's own RFC 8032 verifier, Node `node:crypto`, Rust `ed25519-dalek`) — never a new Sigstore client library, and never a bundle whose model requires a certificate (sigstore-python and sigstore-rs cannot verify a key-only bundle at all; this is why every binding hand-verifies instead of delegating to one);
4. parse the in-toto **Statement v1** payload and check it against the request:
   - `predicateType` must equal `predicate_types.artifact` (the reference table below);
   - `subject[].digest.sha256` must equal the manifest's own layer digest;
   - the predicate's `abi` must equal `abi_generation` (**never** `abi_revision` — that key name is v0's, and a v1 statement must not be readable as v0 revision 1);
   - the predicate's `os` and `arch` must equal the requested platform;
   - the predicate's `clickhouse_version` must **equal** an exact four-part request, or **lie within** a floating one (a component prefix: `26.8.15.10` is within both `26.8` and `26.8.15`).
   - A duplicate key anywhere in the statement's JSON is `CHTYPES_ARTIFACT_CORRUPT` — every binding's JSON parse refuses one rather than silently taking the last value.

Any of the above failing is `CHTYPES_ARTIFACT_CORRUPT`; no referrer of the signature artifactType verifying under a trusted key at all is `CHTYPES_ARTIFACT_UNTRUSTED`. `CHTYPES_ALLOW_UNSIGNED=1` skips verification with one loud warning, exactly as in v0 — never silently.

The default trust list is the release key below (§0/§4.2 of the delivery side's design: **no rotation for v1**, the same key v0 ships). `CHTYPES_TRUSTED_KEYS` **replaces** the default list, never appends to it. A second, fixture-only test key exists for this repository's own conformance suite (`tests/fixtures/fetch-v1/test-key/`); it is in the generated constants as `TEST_KEYS`, `trusted_by_default: false` always, and is never part of any production build's trust list — a case opts into it explicitly (`request.trust: "test"` in `cases.json`).

**After `dlopen`**, the FFI layer additionally checks the predicate against the loaded library's own build info (`chs_build_info()`) — `abi_fingerprint`, `library_sha256` and `glibc_floor` are carried through by the fetch layer **opaque**: it never interprets them, never checks glibc, and never dlopens. A mismatch there is `CHTYPES_ARTIFACT_INCOMPATIBLE` (§8), raised by the loader, not by this layer; see the FFI lane (not yet built — blocked on the ABI v1 design) and §9 below.

## 5. Bytes and unpack

`GET /v2/<repository>/blobs/<layer digest>`, downloaded to a temp file **while hashing**:

1. check the downloaded size and sha256 against the manifest's layer descriptor **before any decompression** — a `tampered-layer` case must show no unpack attempted and the temp file removed, never a partial decode of untrusted bytes;
2. zstd-decode (multi-frame streams are accepted; a window log above `limits.zstd_window_log_max` is refused as `CHTYPES_ARTIFACT_CORRUPT` before the decoder allocates for it);
3. unpack the tar stream with per-entry checks: **regular files and directories only** — a symlink, hardlink, device file, absolute path or `..` path segment is `CHTYPES_ARTIFACT_CORRUPT`, and so is a duplicate entry name;
4. enforce `limits.max_unpacked_bytes` as the tar stream is written, not after;
5. **re-hash the installed library** against the signed predicate's `library_sha256` and compare its size to `library_bytes` — the same load-time re-verification v0 performs, now against the OCI-delivered bytes.

Every one of the checks above runs **in this order**, and a failure at any step removes whatever partial state it produced — no half-unpacked directory is ever left where a later `--offline` read could find and trust it.

## 6. Lock schema 3 and `--frozen`/`--offline`/`update`

`chtypes.lock`, schema 3 (`spec/fetch-v1/schema/lock3.schema.json`), replaces v0's schema 1 and 2 outright — **a v0 lock is refused** (`CHTYPES_ARTIFACT_PINNED`, naming re-lock), never silently reinterpreted. Per declared platform, it records the request, the exact resolved version and build, and the **platform manifest, layer and bundle digests** — never a hostname, so a lock is mirror-portable. The **index digest is informational only**: under option (a) of the delivery side's design the index is computed by the Worker, not stored, so a by-digest GET of it is not guaranteed to be served, and `--frozen` never fetches it.

- `fetch --lock` resolves normally (§3–§4) and then writes the lock.
- `--frozen` **skips resolution entirely**: it fetches the platform manifest, bundle and layer by digest from any configured base, verifies them exactly as a normal fetch would (§4–§5), and refuses (`CHTYPES_ARTIFACT_PINNED`) if the lock names no entry for the requested platform, or the lock itself fails schema validation. A tree with **no tags, no referrers API and no `tags/list`** still succeeds under `--frozen` — every request it makes is by digest (the `frozen-no-discovery` case).
- `update` re-resolves every locked request against the current index and rewrites the lock; it never merges a stale entry with a fresh one.
- `--offline` reads the cache only (§1): the **source of truth is the immutable `unpacked/sha256/*/verified.json` records**, never `index.json`. A pre-seeded `index.json` entry with no corresponding `unpacked/` directory is the one case `--offline` still verifies and unpacks before answering, because it has not yet produced a `verified.json` record of its own. A directory whose record a reader cannot accept (§1) counts as having none.
- **A lookup creates nothing.** `resolve_installed`, `list_installed`, `verify_installed` and `ensure` with `offline` never create a directory or a file: the layout is made when an install begins, the pre-seed install above included, so a read-only mount reads cleanly and a mistyped `CHTYPES_CACHE` is not created by a lookup. A `chtypes verify` that verified no build says so on stderr, `chtypes: verified 0 builds under <root>`, so an empty pass never looks like a good one (public issue #486).
- Writing a lock for **every platform the index offers**, not only the host's own, downloads and verifies every platform's bundle but fetches the **layer only for the host's own platform** — `lock-write-all-platforms` asserts zero layer `GET`s for non-host platforms.

## 7. The retry table

5 attempts, first wait 4s, ×2 each time; retry on 408, 429, 500, 502, 503, 504; honor `Retry-After` on 429, 503; a `Retry-After` past the remaining budget is refused rather than shortened, and the refusal names the value.

## 9. The seam

The fetch layer is a module with exactly four entry points, identical across all four bindings (spelled per that language's own naming convention) and called from nowhere outside the module except the binding's own loader, once the FFI lane wires it in:

- `ensure(request, options) -> Resolved` — may use the network unless `offline`.
- `resolve_installed(request, platform, options) -> Resolved | MISS` — **never touches the network**; what a loader calls on every `open`.
- `list_installed(options) -> [Resolved]`, `verify_installed(options) -> [VerifyResult]`.
- `fetch_signed(repository, ref, predicate_type, options) -> {path, statement, digests}` — the generic signed-artifact fetch goldens and fixtures reuse, so neither needs its own trust logic.

**Goldens: `fetch_signed` with the goldens predicate type selects a revision.** The registry is append-only, so a corrected goldens set for the same build is published as a SECOND goldens referrer of the same platform manifest, and the first can never be deleted. The artifact producer therefore puts an integer `revision` in the goldens predicate and never reuses one for a different document. For `predicate_type = goldens`, `ref` is a **platform manifest digest** (not the goldens object's own), and `fetch_signed` itself, never a caller or a test runner:

1. lists the platform manifest's referrers filtered by the goldens artifactType (the referrers API first, the `sha256-<hex>` fallback tag only when the API answer has no such referrer, as for signatures). None at all is `CHTYPES_ARTIFACT_UNPUBLISHED`;
2. verifies EVERY candidate: its own signature referrer (accepted if any bundle verifies, as in §4), the statement subject equal to the candidate's blob digest, and the predicateType. A candidate that fails is skipped: it is never chosen and never causes a tie. If no candidate verifies, the first failure's error is raised (`CHTYPES_ARTIFACT_UNTRUSTED` for a signature that verifies under no trusted key, `CHTYPES_ARTIFACT_CORRUPT` for a statement that is wrong);
3. reads `revision` from each VERIFIED candidate's predicate, straight from the signed bytes. It must be a JSON integer written without a fraction, exponent, sign or leading zero, at most 2^53 - 1: a missing key, a boolean, a string, null and a float such as `1.0` are all `CHTYPES_ARTIFACT_CORRUPT`. A verified candidate with an unusable revision is never skipped, because it could be the newest document and choosing an older set would be the stale pick this rule exists to prevent;
4. chooses the verified candidate with the HIGHEST revision. Two or more at that revision with DIFFERENT blob digests are a tie, refused as `CHTYPES_ARTIFACT_CORRUPT` with a message naming both digests and the revision; the same blob digest under the same revision (two bundles, say) is one document, not a tie.

**The request is checked against the SIGNED predicate on every resolution path.** `ensure`, `resolve_installed` and the pre-seeded and already-unpacked cache entries alike answer a request only with a build whose signed `clickhouse_version` equals an exact request or lies within a floating one (§4). No local label (an `index.json` annotation, an `installed.json` entry, a directory name) stands in for the signed version. A request an installed build does not satisfy is `CHTYPES_ARTIFACT_MISSING` under `--offline` and from `resolve_installed` (reported as a miss), and `CHTYPES_ARTIFACT_PINNED` under `--frozen` when the lock names no entry for it (§6).

**A newer install is kept only within the request.** When `ensure` resolves a request online and the registry offers a build OLDER than one already installed, the installed build is kept and returned with a warning that names `monotonic`, rather than replaced by an older one, whether or not the offered build is installed too: a mirror or a rollback can offer an older build, and a cache never goes backwards on its own. Only an install whose signed `clickhouse_version` lies within the request counts, and the newest such install is the one kept:

- for a line request (`26.3`), a newer build of that line: a later patch, or the same version with a later `build`;
- for an exact request (`26.3.38.2`), a newer `build` of that exact version only. No other version answers an exact request, newer or not.

An install of another line never answers a request. A request that is not a version spelling (an arbitrary tag) names no range, so nothing is kept for it. The `request-scope-*` cases (§10) pin this in every binding. Public issue #481 is why: Go and TypeScript compared the offered build with every install for the platform, so a line with no install of its own was answered by a higher line already in the cache.

**The load-time assertion.** After every open through a registry (a request for a version, or `preload`), the loaded library's own `build_info` `clickhouse_version` must equal an exact request or lie within a floating one, whatever the cache answered. Otherwise the open fails as `CHTYPES_ARTIFACT_CORRUPT`, the code §4 gives a signed version outside the request, as a loader refusal with reason `build_info_mismatch:clickhouse_version`, `want` the request and `got` the library's version. The image stays loaded for the requests it does answer, because no binding unloads a library. A request that is not a version spelling is not checked, and `open_unverified` takes no request, so it is not checked either.

A `Resolved` carries: `abi_generation` (always 1); `platform`, `request`, `version`, `channel` (from the predicate, when present) and `build`; `library_path` (absolute) and `dir` (`<layout>/unpacked/sha256/<manifest-hex>`); `digests {index?, manifest, layer, bundle, bundle_manifest?}`; the verified `predicate` object verbatim (including `abi_fingerprint`, `library_sha256`, `library_bytes` and `glibc_floor`); `signed_by` (the key id, or `""` under allow-unsigned); `source` (a base URL, `cache`, or `system:<dir>`); `already_installed`; and `warnings[]`.

**On return, the fetch layer guarantees:** the library file exists and its sha256/size equal the signed predicate's; the predicate verified under a trusted key (or allow-unsigned was explicit and loud); `predicate.abi == abi_generation`; the predicate's `os`/`arch` equal the request's platform; the predicate's version lies within (or equals) the request.

**The fetch layer never:** `dlopen`s anything; interprets `abi_fingerprint` (passed through opaque); checks glibc; or reads a `chs_*` symbol. Those checks — and the `CHTYPES_ARTIFACT_INCOMPATIBLE` error code they can raise (§8) — belong to the FFI/loader lane, not yet built as of this writing (blocked on the ABI v1 design, core issue #647). When it lands, it calls `resolve_installed` and `ensure` exactly as any other caller of this module would; the seam above is frozen specifically so that lane can be written against it without this module changing underneath it.

## 10. Conformance

Every fixture under `tests/fixtures/fetch-v1/` — route trees, OCI image layouts, scripted HTTP responses, locks and `cases.json` itself — is generated by `scripts/fetch-v1/genfixtures/` (its own Go module; `cd scripts/fetch-v1/genfixtures && go run . --write`), except `tests/fixtures/fetch-v1/{test-key,other-key}/` (hand-generated ed25519 keys, read but never written by the generator) and `tests/fixtures/fetch-v1/layouts/oras-preseed/` (written only by a real `oras copy -r --to-oci-layout`, in the `v1-oras-preseed` workflow job). The generator is deterministic — no timestamps, no randomness — so `go run . --check` (regenerate into a temp directory and diff) is the drift gate, and `go run . --selftest` proves that gate actually catches drift, on a throwaway copy.

### Running the suite locally

```bash
cd scripts/fetch-v1/genfixtures && go run . --write   # regenerate every fixture
python3 scripts/fetch-v1/schema_check.py               # validate cases.json, http/*.json, locks/expected/*.json
python3 scripts/fetch-v1/server.py --fixtures "$(pwd)/tests/fixtures/fetch-v1" --port 0
python3 scripts/fetch-v1/parity.py --reports-dir <dir-of-report-*.json>
```

`server.py` prints `LISTENING <port> <port2>` once it is ready: `<port>` is the primary origin every HTTP-transport case's `{base}` expands against, `<port2>` is a second origin used only by cross-origin-redirect cases. The server runs until killed; a conformance runner starts one instance, runs every HTTP-transport case against it, and reads `GET /_log/s-<case-id>` afterward for whatever its own assertions need from the raw request log (headers included) that a `cases.json` `expect` field has no room for — see "Known gaps" below.

### The runner contract

Each binding ships one runner, gated on `CHTYPES_V1_CONFORMANCE=<abs path to tests/fixtures/fetch-v1>` (unset: skip loudly by name, never a silent pass). It executes every case on every transport `cases.json` lists for it, starting `scripts/fetch-v1/server.py` itself for any case listing `http`. The exact commands `v1.yml`'s `v1-conformance` matrix runs (plan §3.3, frozen; none of these per-binding test files exists yet, so none is cited here by path — each binding lane adds its own): Go, `go test -count=1 -run '^TestConformanceV1$' ./internal/ocifetch/`; Python, `uv run pytest -q` on its own `ocifetch` conformance module; TypeScript, `pnpm exec vitest run` on its own `ocifetch` conformance spec; Rust, `cargo test --features fetch-v1 --test ocifetch_conformance`. CI runs each of them with no network but loopback, in a network namespace entered for that process tree alone (`scripts/fetch-v1/sandbox.sh`, which also proves itself with `--selftest` on every pull request): a runner that needs the internet fails there, not on a user's machine.

**`{base}` per transport** (§2, §4): `file://<abs>/tests/fixtures/fetch-v1/trees/<tree>/v2/chtypes/v1`; `http://127.0.0.1:<port>/s-<case-id>/chtypes/v1` (a conformant client always splices its own `/v2/` in immediately after the scheme and authority, the same place a real repository name sits — `default_bases` in `constants.json` has no `/v2/` in it either, for the same reason — so the full wire path becomes `/v2/s-<case-id>/chtypes/v1/...`, which is exactly what `server.py` parses); `https://registry.test:5443/chtypes/v1` (the `v1-network` job's own `registry:2`); for a staging run, whatever `CHTYPES_V1_REGISTRY_BASE` names (see "The staging run").

**`{base2}`** (http transport only; decided here, lane 0B, 2026-10-02): the same `s-<case-id>/chtypes/v1` suffix as `{base}`, but rooted at `server.py`'s SECOND origin — the second port on its `LISTENING <port> <port2>` line — for a case that needs two genuinely independent bases over the same case id, such as a mirror-failover case (`mirror-failover-5xx`, `mirror-failover-digest-404`): base[0]'s scripted failures exhaust against `routes`, base[1] (`{base2}`) is served from that same script's `second_origin_routes`, with its own response-sequence cursor (`server.py` keys its cursor on `(case id, origin, method, path)` precisely so a second-origin route never shares state with the first-origin route of the same path).

**Writing `CHTYPES_V1_REPORT`** (`report.schema.json`): one JSON file per toolchain leg, `{"schema":1,"binding":"go","toolchain":"go1.27.x","cases_sha256":"<sha256 of the head's cases.json>","results":[{"id":...,"transport":...,"verdict":"pass"|"fail","detail":"..."}]}`. The `v1-network` job's own report (registry-transport results only, for the five cases below) uses the toolchain value **`"registry"`** — a sentinel `parity.py` recognizes; it is never one of the matrix's real per-binding toolchain strings. Every report is uploaded `if: always()`, named `report-<binding>-<toolchain>.json`, whether its job passed or failed — `v1-parity` needs to see a _missing_ report as distinct from one that ran and failed.

**`CHTYPES_V1_TOOLCHAIN`** names the report's `toolchain` field exactly as the matrix and `parity.py` spell it (`go1.27.x`, `3.13`, `node24`, `1.87`, ...). `v1.yml` exports it from the matrix leg (`registry` in the `v1-network` job); a runner uses it verbatim when set and falls back to its own mapping of its runtime version otherwise. A runtime's own patch version (`go1.27.1`) is rejected by `parity.py`.

**The registry report.** The runners take no registry-only switch: with `CHTYPES_V1_REGISTRY_BASE` set they run every transport. The `v1-network` job therefore keeps only the `registry` rows of each runner's raw report and writes them as `report-<binding>-registry.json` with `toolchain` `registry`; the file and http rows are judged by the `v1-conformance` legs. The job's `registry:2` is loaded by `scripts/fetch-v1/push_tree.py` with every tree a registry-transport case names. TLS is never configured per binding: the throwaway CA is installed in the OS store and each binding must trust it from there (Node via its documented `--use-system-ca` option).

**Enrollment:** add `spec/fetch-v1/enrolled/<binding>` (an empty file) in your own binding's PR, never another's. `parity.py` refuses a run where the enrolled set has shrunk since `v1`'s own tip.

### The generic-fetch convention

A case id starting `goldens-` or `fixtures-` exercises `fetch_signed(repository, ref, predicate_type)` (the seam, §9) instead of `ensure()` — not a separate case shape (lane 0A's `cases.schema.json` has none, and extending the frozen contract is not this lane's call to make). `request.spelling` carries the bare `sha256:<hex>` ref to resolve — a goldens referrer's own manifest digest, or (for `fixtures-digest-pin-no-tag-fallback`) the SDK's own fetch-fixtures artifact's manifest digest in its own repository (`chtypes/v1/sdk-fetch-fixtures`) — and `expect.manifest`/`expect.library_sha256` name that artifact's own digest and content hash, never a platform manifest's.

A case id starting `resolve-installed-` exercises `resolve_installed(request, platform, options)` (the cache-only seam entry, §9) instead of `ensure()`, on the same `setup.cache`; a miss (the seam's `MISS`) is reported as `CHTYPES_ARTIFACT_MISSING`, the code `--offline` gives, so `expect` is unchanged. For `goldens-` cases `request.spelling` is the PLATFORM manifest digest and `expect.manifest` / `expect.library_sha256` name the CHOSEN goldens document's manifest digest and content hash.

**Goldens revision cases** (§9): `goldens-revision-highest` (revisions 1 and 2, 1 listed first: the revision-2 document), `goldens-revision-tie` (two different documents, both revision 3: `CHTYPES_ARTIFACT_CORRUPT`), `goldens-revision-missing` (no `revision`: `CHTYPES_ARTIFACT_CORRUPT`), `goldens-revision-unverified-higher` (revision 5 with a bad signature is skipped, revision 4 wins), `goldens-revision-same-doc` (one blob under revision 2 with two bundles: ok), and `goldens-revision-not-integer-bool` / `goldens-revision-not-integer-float` (`true`, `1.0`: `CHTYPES_ARTIFACT_CORRUPT`).

**Request-scope cases** (§9, public issue #481): the `request-scope` tree serves two lines, `26.3` (offering `26.3.4.1`) and `26.8` (`26.8.5.1`), and every case is online, so the registry resolves the request before the cache is consulted. With `26.8.5.1` installed, `request-scope-lower-line` (`26.3`) and `request-scope-lower-exact` (`26.3.4.1`) must fetch and answer `26.3.4.1`. With `26.3.9.1` installed, a newer build of the same line that the registry never offers, `request-scope-newer-in-line` (`26.3`) must keep `26.3.9.1` with the `monotonic` warning, and `request-scope-exact-in-line` (`26.3.4.1`) must answer `26.3.4.1`. With both installed, `request-scope-newer-beside-offered` (`26.3`) must still answer `26.3.9.1` with the warning, and `request-scope-exact-beside-newer` (`26.3.4.1`) must answer `26.3.4.1`.

**Root-order cases** (§1, public issue #486): two layouts, `root-order-older` and `root-order-newer`, each hold one canonical record and its library for a build of `26.2`, and nothing else. `root-order-system-newer` uses the older as the cache and the newer as a system directory, and `root-order-cache-newer` the reverse; each runs through `--offline` and through `resolve_installed`, and both must answer with the newer build. A binding that stops at the first root with a match, or never reads a system directory's records, answers the first with the older.

**Request-versus-signed-version cases** (§9): `installed-request-*` and `resolve-installed-request-*` install one signed build, `26.8.15.10`, and request it as `1.1`, `26.9` and `26.8.15.9` (never resolved) with `26.8` and `26.8.15.10` as controls, each through `--offline`, `resolve_installed` and `--frozen` (a lock pinning only the two matching spellings). `label-mismatch-*` plants the ref name `26.9` on the index entry of that same build, installed or only pre-seeded: a request for `26.9` must miss, and `26.8` (the signed version) is the control.

### Cache fixtures and `installed.json`

A `layouts/<name>/` fixture (`setup.cache` names one) is a plain OCI image layout — `oci-layout`, `index.json`, `blobs/sha256/<hex>` — the same shape a real `oras copy --to-oci-layout` produces, with two kinds of exception. **Most layouts carry no pre-populated "already unpacked" directory.** Every binding's fetch layer must treat a pre-seeded `index.json` entry with no corresponding `unpacked/` directory as unverified — verify-then-unpack from local blobs, zero network — so most cache cases (`offline-hit`, `offline-miss`, `preseed-oras`, `system-dir-readonly`) need nothing more than the layout itself.

**The `cache-record-*` and `upgrade-0x-*` layouts DO carry an `unpacked/` directory, and the generator writes the `verified.json` in it.** This amends the earlier rule that a fixture never carried one, which held while each binding kept a private record format: `verified.json` is now the one canonical record (§1), so a fixture can carry it, and the only way to prove every binding READS the canonical record is to hand each a layout that already has one. The generator writes the record from the artifact's own digests, never by running a binding. `cache-record-canonical` has the record, the library and no blobs and no `index.json`, so it passes only if the record was read and trusted. `cache-record-foreign-unparsable`, `-flat` (the old flat shape) and `-schema2` (a `schema: 2` record naming a build no real artifact has) carry blobs and an `index.json` entry with an unreadable record: every binding must treat the record as absent, re-verify from the blobs, and answer with the real build. `upgrade-0x-registry` is a raw layout with no `oci-layout` and no `index.json` at all (`<minor>/manifest.json`, a library, `patches/…`): offline is not installed, and the online case `upgrade-0x-registry-online` installs a build into it. `upgrade-0x-unpacked-noblobs` and `-reverify` hold a 0.x-style `manifest.json` where `verified.json` belongs, without and with blobs. Each is run through `--offline` and through `resolve_installed` (the `resolve-installed-` id prefix). `scripts/fetch-v1/schema_check.py` validates the record in every `cache-record-canonical*` layout against `verified.schema.json`.

**`preseed-oras` is CONDITIONAL on `layouts/oras-preseed/` actually being on disk, checked fresh on every `--write`/`--check`/`--selftest`.** That directory is written only by a real `oras copy -r --to-oci-layout` in the workflow_dispatch-only `v1-oras-preseed` job, never by this generator — and as of this writing that job has not yet landed its output in this tree. Rather than ship the case unbacked (a `setup.cache` naming a directory that cannot exist, which every binding's runner would either 404/ENOENT on or have to special-case around — a GENERATOR problem presented as a binding one, the exact defect three fetch lanes independently found, 2026-10-02), `cachecases.go` gates the case's very presence in `cases.json` on `layoutPresentOnDisk("oras-preseed")` and otherwise skips it LOUDLY (a stderr line, every run, never silent — the same discipline `CHTYPES_V1_CONFORMANCE` unset already follows, above). Dispatching the job and committing its output is enough to pick the case back up on the next regeneration; no binding needs a second wiring pass. `checkCacheLayoutsExist` (`cases.go`) is this same invariant's second, independent check.

Some cases (`existing-install-noop`, `monotonic-warning`, `offline-newest-of-two`/`offline-newest-build`, the `request-scope-*` cases) need something to already be **installed**, not merely present, before the case begins. For these, the layout root also carries `installed.json`: `{"installed": ["sha256:<manifest digest>", ...]}` — a **test-setup instruction for the conformance runner**, read before the case starts ("call your own `ensure()`/unpack path against exactly these manifest digests, offline, from these local blobs, before starting the clock"), never a file any binding's shipped cache code parses at runtime. This is a decided-here convention (lane 0B), not part of lane 0A's frozen contract.

**`existing-install-noop`'s assertion is "zero LAYER requests," not "zero requests at all."** The case is ONLINE, not `--offline` — the manifest and signature bundle may legitimately be re-resolved over the network to confirm the already-installed build is still the one the line now offers — so `expect.requests.max` is not the right shape for it. What must never happen is a `GET` for the layer blob itself, since the already-installed bytes already satisfy it: `expect.requests.none_matching` names exactly that one path, `["GET .*/blobs/<layer digest>"]`, scoped to the layer only. (This case and `index-race-reapply`, alongside it in `cachecases.go`'s "cache" tree, originally published their manifests under a `c-<id>`-shaped symbolic tag instead of their own version spelling — so `index-race-reapply`, which never resolves `--offline`, could never find a tag to resolve against at all, and `existing-install-noop` likewise. Fixed here, lane 0B, 2026-10-02 — tagged under their real version spellings now, with `checkOnlineTagsExist`, genfixtures' own generator self-check, panicking on any future case shaped the same way.)

### `layouts/basic` and the registry job

`layouts/basic/` is the one layout `v1-network` pushes into `registry:2` whole: its root entry is the full multi-platform **index** for tag `26.8.15.10` (every platform fans out from it), matching what a real push publishes. Every other layout in this tree roots at ONE platform's manifest directly (the shape a real `oras copy --platform <p> --to-oci-layout` produces) — **measured locally, oras 1.3.4: a layout with several same-tagged single-platform root entries resolves ambiguously, to just one of them**, which is why `layouts/basic` is built differently (`copyIndexIntoLayout` in `layout.go`, not `copyArtifactIntoLayout`).

**Also measured locally (oras 1.3.4):** `oras cp -r --from-oci-layout` does **not** copy referrer artifacts from a local OCI layout source — `-r`'s referrer discovery goes through the Referrers API (or the fallback-tag convention), neither of which a plain directory implements. The `v1-network` job's push step therefore moves only the index and its platform manifests; a following step attaches the linux-arm64 signature bundle directly (`oras attach`, reading the bundle bytes straight from the tree fixture) so the job's own "record registry:2's referrers behavior" step has something real to observe. This is a gap in `oras`'s layout-source support, not in `registry:2` or in this fixture — a real producer push (blocked on the delivery side, plan §1.2) will use its own mechanism and is not expected to hit it.

**`registry:2`'s referrers behavior — measured, CI run 36965426062, job "v1-network," 2026-10-02** (both GETs sent the `Accept` header `manifest-accept-header` already requires; the first measurement, without it, read the fallback tag as absent when it was only unnegotiated): `GET /v2/chtypes/v1/referrers/<digest>` answers a real `404 page not found` — this stock `registry:2` image does not implement the referrers API — but `GET /v2/chtypes/v1/manifests/sha256-<hex>` answers `200` with `{"schemaVersion":2,"mediaType":"application/vnd.oci.image.index.v1+json","manifests":[{...,"artifactType":"application/vnd.dev.sigstore.bundle.v0.3+json"}]}`, naming the pushed signature bundle exactly. `oras attach`'s default (`--distribution-spec unknown`) writes that fallback tag itself once it detects the referrers API is absent, so every `no-referrers-api-uses-fallback-tag`-shaped host this job can reach is in fact discoverable, just not through the API half.

### The staging run

The `v1` workflow's `v1-staging` job is the first fetch over real HTTPS through the delivery side's host: its CDN cache, its real referrers API and any real redirects, none of which the loopback server or `registry:2` can show. It is dispatch-only and never a required context.

**Dispatch it:** run the `v1` workflow by `workflow_dispatch` with `registry_base` set to the staging host's base, repository path included and no trailing slash (for example `https://registry-staging.wavehouse.dev/chtypes/v1`). Left empty, nothing runs. Dispatch from a ref with no other `v1` run in flight, because the workflow's concurrency group cancels the older run on the same ref.

**It does not run in the no-network sandbox** (`scripts/fetch-v1/sandbox.sh`) the ordinary conformance legs use, because it exists to reach a live host.

**What it runs.** One leg per enrolled binding (a binding with no marker under `spec/fetch-v1/enrolled/` or no runner file skips loudly), each running that binding's own conformance runner unchanged. `scripts/fetch-v1/staging.py emit` first derives a case table from `cases.json`: only the cases a real host can answer with nothing scripted, repointed to the `registry` transport alone. `staging.py`'s docstring lists the nine exclusion rules; each excluded case is printed with the rule that excluded it. Today that is the plain online resolves over the `basic` tree (the one tree the delivery side staged); every case that needs a scripted response, a seeded cache, a lock, an environment variable or a request-log assertion is excluded. The staged tree's tags are the host's, and an index there is compact JSON with its own key and platform order, so index digests differ from the fixture tree's; a case asserts a platform manifest's digest, which the host serves unchanged (`measured` for `26.8`, 2026-10-03; `unverified` for the other tags until the first run).

**Trust is opt-in, and only here.** The staged fixtures are signed with the SDK TEST key, which is never in a default trust list. `emit` refuses to write anything unless it is handed that key's own public hex (`--trust-test-key`, which must equal `tests/fixtures/fetch-v1/test-key/public.hex`), the job passes it in exactly one step, and the derived table's cases carry `request.trust: "test"`. The staging host removes the test key from its trust once the artifact producer's first push lands, and the fixtures with it; after that this job has nothing to run against.

**The runner contract.** Environment variables, the same for every binding:

- `CHTYPES_V1_CONFORMANCE`: the derived fixtures directory (symlinks to the real one, plus the derived `cases.json` and a `staging-manifest.json` sidecar runners never read).
- `CHTYPES_V1_REGISTRY_BASE`: the `{base}` for a `registry`-transport case, replacing the loopback value. When it is unset a runner skips its `registry` pairs, as it does under the ordinary matrix.
- `CHTYPES_V1_REPORT`: where to write the report, as in the ordinary matrix. The report's `cases_sha256` is the derived table's.

**Per-case differences are recorded, never silent.** `OVERRIDES` in `staging.py` replaces a case's expected outcome on the real host and carries its reason into the summary; `NOTES` records a wire difference that does not change the outcome. `missing-platform` is the one note today: the host never serves a partial set, so tag `26.6` is a 404 there (`measured`) where the fixture tree serves a 200 index without the platform, and the expected `CHTYPES_ARTIFACT_UNPUBLISHED` should be the same either way (`inferred`, from the tag-404 rule in §7).

**The verdict** is the `v1-staging-verdict` job's summary: one row per derived case, one column per enrolled binding, the notes, and the excluded cases with their rules. Its exit status is 0 whatever it says, `v1-parity` never reads it (the reports are uploaded as `staging-report-*`, which `v1-parity`'s `report-*` download pattern does not match), and it never gates a PR.

**What it proves, and what it cannot.** It proves that each enrolled binding's real client resolves, verifies and fetches from the delivery side's host over HTTPS, through its cache and its referrers API, to the digests the fixtures name. It cannot prove anything about behavior a host will not perform on cue (retry, `Retry-After`, redirects dropping credentials, mirror failover, stalls), anything about trust failures (the host holds only validly signed data), or the cache, lock and offline cases. Those stay with the loopback server. Nor does it say the production host behaves the same: it is a staging host and a test key.

### Known gaps (report these against this guide, not against a case's `ok`/`code`)

- **`download-token-sent`, `manifest-accept-header`:** `cases.schema.json` has no field for "this header must have been sent" — only `requests.none_matching` (absence). Both cases are enforced by `server.py` itself refusing (400/second 401) when the required header is missing or wrong, which is why they have no declarative `http_script` response sequence doing the real work; see `server.py`'s own header comment.
- **`spelling-refused`/`spelling-refused-v-prefix`:** refused before any network call, by a client-side regex check, which is not one of the shared error codes (`errors`, above) — `expect.code` is `null` for these two; `expect.requests.max: 0` is the real assertion.
- **The `hint` field of every bundle this repository signs is our own keyid** (the `sha256-first16hex` scheme every binding already computes for v0), never a raw-key encoding. Nothing in layout-v2 spec §4.2 fixes the hint's content beyond "a public-key hint" — none of this repository's four hand-rolled verifiers select a key BY the hint (they try every trusted key), so the format is this generator's own choice, recorded here so a reference-verifier integration (`scripts/fetch-v1/refcheck/`) keys its own trust mapping by the same string.
- **`scripts/fetch-v1/refcheck/` is a representative sample, not an exhaustive cross-check.** It verifies a handful of known-good bundles (one per predicate type this repository signs anything with) against sigstore-go, `@sigstore/verify` and `cosign verify-blob-attestation`, report-only. The plan's broader vision — cross-checking every fixture's trust verdict against all three reference verifiers — is future work, not this lane's acceptance bar.
- **sigstore-go: the delivery side's design doc cites version "1.3.0"; that version does not exist on the Go module proxy as of 2026-10-01** (the newest published tag is v1.2.2, which `refcheck/go` pins and which verifies this repository's bundles). Recorded here rather than silently substituted.
- **Every referrer manifest's config blob must physically exist, not only be embedded via the descriptor's `data` field.** Measured against a real registry host (the artifact producer's own push of `trees/basic`, 2026-10-02): a manifest PUT whose config digest has no backing blob is refused `400 BLOB_UNKNOWN`, `data` field or not. `genfixtures` registers the `{}` empty config (`sha256:44136fa355b3678a1146ad16f7e8649e94fb4fc21fe77e8310c060f61caaff8a`) as a real blob in every tree and layout that has a referrer manifest, alongside the embedded `data` convenience.
- **`missing-platform`'s partial tag (`26.6`, linux-amd64 and linux-arm64 only, darwin-arm64 omitted) is checked against the real host's behavior.** The real host never serves a partial set at all (an incomplete line's tag is a 404, not a 200 with a short index), so this fixture's WIRE SHAPE differs from the real host's — but no case requests a platform the partial tag _does_ carry expecting success, so the client-observable outcome (the requested platform is unavailable, `CHTYPES_ARTIFACT_UNPUBLISHED`) matches either way. Confirmed by grep (`command grep -n "26\.6" scripts/fetch-v1/genfixtures/*.go`): `26.6` is cited exactly once, as `missing-platform`'s own tag, requesting the platform it omits.
- **Follow-up, not done in this change:** the real host's index JSON is compact with a different key and platform order than this generator's (indented, insertion order); layout-v2 spec §5.1 now pins the host's canonical form. Locks pin whichever digest they actually receive, so nothing here is broken by the difference — but a later change should regenerate every fixture index in that canonical form so fixture digests match the host's byte-for-byte, which would also let a future cross-check diff fixture bytes against a live pull directly.
